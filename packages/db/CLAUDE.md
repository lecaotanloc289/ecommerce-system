# @repo/db

Prisma schema (DB source of truth), client singleton, ledger + money boundary helpers, seed.

## State

- Schema: 42 models, 28 enums (identity, vendor/KYC + staff invitations, catalog+i18n, cart, orders, payment+ledger+refunds, coupons, reviews, settings, outbox, Zalo notifications, vendor CRM, live shopping).
- Migrations: `init`, `add_search_indexes` (pg_trgm + tsvector, hand-written SQL), `register_search_vector` (registers the generated `search_vector` column via `Unsupported("tsvector")`), `add_platform_coupon_code_unique` (partial unique index so platform coupons — `vendor_id IS NULL` — have globally-unique codes; Prisma's `@@unique` can't express a `WHERE` clause), `widen_money_columns_to_bigint` (every money column int4 → int8; hand-edited to strip the search-index drift statements below), `add_marketplace_ops_fields` (roadmap T0.1 — every column/table later waves need; hand-edited for the same drift, plus the hand-written partial unique index `refunds_sub_order_id_active_key`), `add_payment_provider_ref_and_client_ip` (roadmap T2.2 — `Payment.providerRef` + `clientIp`; hand-edited for the drift), `add_zalo_notifications` (generated with `migrate diff` between schema versions — no drift statements), `add_live_sessions` (`LiveSession`, `LiveSessionProduct`, `LiveSessionStatus` / `LiveEndReason`, `PlatformSettings.live_disconnect_grace_seconds` / `live_chat_cooldown_seconds`; drift statements stripped), `add_live_session_partial_indexes` (hand-written: at most one `LIVE` session per vendor, at most one pinned product per session), `add_outbox_pending_index` (hand-written partial index `outbox_events_pending_idx` on `(created_at, id) WHERE processed_at IS NULL`). The three live migrations were written on a parallel branch and re-timestamped after `add_zalo_notifications` when merged (they had not been applied to any shared database), so the history is linear; all three are additive.
- `add_vendor_crm` (vendor CRM, `docs/superpowers/plans/2026-11-23-vendor-crm.md` K2): `vendor_customers` (tags, GIN index), `vendor_customer_notes`, `customer_vendor_preferences` (consent + sha256 unsubscribe token hash), `crm_automations` (unique per vendor+kind), `crm_campaigns`, `crm_messages` (unique `(campaign_id,user_id)` and `(automation_kind,sub_order_id)`), `notifications`; `PlatformSettings.crm*` thresholds (60/180/3/2/2); `sub_orders(vendor_id,status)` index. Hand-edited for the same search-index drift. Seed adds 5 vendor-A CRM demo customers (`crm-new|returning|vip|at-risk|lapsed@example.com`, fixed-date COMPLETED sub-orders; segments hold for `CRM_SEED_REFERENCE_DATE` = 2026-11-23 — new 2026-11-10, returning 2026-09-20/11-01, vip 08-15/10-05/11-15, at-risk 2026-08-01 + a newer CANCELLED order that must not count, lapsed 2026-03-01), 1 marketing opt-in (vip), 1 note, enabled `THANK_YOU` automation.
- `add_vendor_crm_constraints` (follow-up, `add_vendor_crm` stays untouched): FK indexes, hand-written partial index `crm_messages_due_idx ON crm_messages(scheduled_for) WHERE status='SCHEDULED'` (replaces the `(status, scheduled_for)` composite: the worker only scans SCHEDULED rows, a partial index is smaller and cheaper to maintain), CHECK `crm_messages_source_check` (a message has exactly one source: a campaign, or automation*kind + sub_order_id), CHECKs on `platform_settings.crm*\*`(each 1..3650,`crm_at_risk_after_days < crm_lapsed_after_days`), `CrmMessage.subOrder`FK`Restrict`, nullable + `SetNull` `VendorCustomerNote.authorId`/`CrmCampaign.createdById`(deleting a staff user must not fail), and the append-only`crm_consent_events` table (`ConsentAction`).
- CRM consent rules: marketing consented iff `marketing_opt_in_at IS NOT NULL AND (marketing_opt_out_at IS NULL OR marketing_opt_in_at > marketing_opt_out_at)`; service messages allowed iff `service_opt_out_at IS NULL`. Every consent change ALSO appends a `crm_consent_events` row (action, source, time) as evidence; events are never updated, only cascade-deleted with the user/vendor. The unsubscribe token is deterministic `HMAC(secret, userId:vendorId)`; `unsubscribe_token_hash` is the sha256 hex of it, used for lookup only.
- Seed CRM fixtures: shipping 30 000, commission 10% and discounts are hardcoded to mirror PlatformSettings / vendor A's Standard shipping / coupons; the 9 demo orders have no Payment, ledger or redemption rows. Segment tests must use `CRM_SEED_REFERENCE_DATE` as `now`. Also seeds one `MARKETING_OPT_IN` consent event for crm-vip.
- Ops fields (roadmap D2/D7/D8/D11/D12/D14 — `docs/superpowers/plans/2026-11-23-marketplace-roadmap.md`):
  - `Payment.redirectUrl` / `expiresAt` / `providerRef` — written by the worker (`@workers/jobs`) after `createSession`, only `WHERE status = PENDING`; null until the session exists. `providerRef` = VNPay `vnp_CreateDate` (its refund needs it) / Stripe session id. `Payment.clientIp` — customer IP stored by the API at checkout / payment retry (VNPay `vnp_IpAddr`); null on rows from before T2.2. It is personal data kept with the payment record (no retention job yet — add one with the outbox cleanup if required). `Order.paymentDeadlineAt` + `PlatformSettings.paymentTimeoutMinutes` (default 30) drive payment expiry.
  - `SubOrder.discountAmount` = **vendor-funded** discount (VENDOR coupons, lowers the commission base); `SubOrder.platformDiscountAmount` = this sub-order's share of PLATFORM coupons (platform-funded, never lowers vendor net or commission). Fulfilment: `carrier`, `trackingNumber`, `shippedAt`, `deliveredAt`, `cancelledAt` (+ existing `completedAt`).
  - Moderation: `ProductStatus.BLOCKED` + `Product.blockedReason`; `Vendor.suspendedReason`.
  - `OutboxEvent.nextAttemptAt` (default now) — dispatcher polls `processed_at IS NULL AND next_attempt_at <= now()`, index `(processed_at, next_attempt_at)` (replaced the `processed_at`-only index).
  - `Refund` (`refunds`, `RefundStatus` PENDING/SUCCEEDED/FAILED): full refund of one sub-order. DB allows **at most one non-FAILED refund per sub-order** (partial unique index → Prisma `P2002`); a FAILED one may be retried. FKs to sub-order/payment/user are `Restrict` (money history).
  - `VendorInvitation` (`vendor_invitations`): store `email` lowercase and only the token **hash** (`tokenHash` unique); cascades with the vendor.
- Zalo notifications (roadmap D16; `workers/zalo/CLAUDE.md`), all cascading with the vendor:
  - `ZaloAccount` (`zalo_accounts`, one per vendor, `ZaloAccountStatus` ACTIVE/EXPIRED/DISCONNECTED): `credentials` is AES-256-GCM ciphertext only `workers/zalo` can read — never return or log it; `zaloUid` unique (one Zalo account per shop), cleared on disconnect.
  - `ZaloMessageTemplate` (`zalo_message_templates`, unique `(vendorId, event)`, `ZaloMessageEvent`): no row = disabled; `delayMinutes` only for AFTER_DELIVERY.
  - `ZaloMessage` (`zalo_messages`, unique `(subOrderId, event)`, `ZaloMessageStatus` PENDING/SENDING/SENT/SKIPPED/FAILED): a Zalo-specific outbox written in the order transaction; `skipReason` holds a core `ZaloSkipReason`.
  - `Order.zaloOptIn` (default false): checkout opt-in; only opted-in orders get messages.
- `src/zalo-queue.ts` — `queueZaloMessages` / `queueZaloStatusMessages(tx, …)`: the Zalo message outbox insert, shared by the API and `@workers/jobs` (every `SubOrder.status` writer calls it in its transaction; contract in `server/CLAUDE.md` "Zalo notifications").
- CRM queries shared by the API and the worker (`src/crm.ts`, exported from the root): `crmSegmentThresholds(db)` (PlatformSettings C3 thresholds), `crmSegmentCutoffs`, `crmAudienceParams`, `crmAudienceIds(db, vendorId, filter, now, thresholds, limit)` — the campaign audience SQL (customers ∩ filter ∩ marketing consent). Here because `workers/jobs` cannot import `server/`; its segment CASE must match core `classifyCustomer` and the copies in `server/src/crm/crm-customers.repository.ts`.
- Live shopping: `LiveSession` lifecycle `SCHEDULED → LIVE → ENDED` (or `CANCELLED`), owned by `server/src/live` and `workers/outbox` — see `docs/superpowers/plans/2026-11-23-live-shopping.md` §1.8. `liveInputId` / `recordingVideoId` are Cloudflare Stream uids; stream keys are never stored. Seed adds one `ENDED` (with replay) and one `SCHEDULED` session for vendor A, both pinning the seeded `basic-tee` + `straight-jeans`.
- Client: singleton in `src/client.ts`, exported as `prisma` from `src/index.ts`. NEVER export the `PrismaClient` constructor outside this package.
- IDs: ULID supplied at create-time (no DB default). Use `ulid()` from the `ulid` package. Seed rows use the fixed canonical ULIDs in `src/seed-ids.ts` (`01SEED…`), so they parse through `@repo/core` id schemas. A local DB seeded before these ids existed (`vendor_a`, …) needs `pnpm db:reset` — the new seed collides on unique slugs/emails.
- Seed demo data (all VND, emails lowercase, tests may reference `SEED_IDS`): users `customer@example.com` (CUSTOMER, `demoUser`), `admin@example.com` (PLATFORM_ADMIN, `adminUser`), `vendor-a@example.com` / `vendor-b@example.com` (VENDOR_OWNER); ACTIVE vendors `vendor-a` / `vendor-b`, each with a zero-balance Wallet; shipping methods A Standard 30 000 / 3d, A Express 50 000 / 1d, B Standard 25 000 / 4d; categories `thoi-trang`/`apparel` and `nha-cua`/`home-living` under an untranslated root; ACTIVE products (vi + en) `basic-tee` (A, SKU `TEE-BLK-M`), `straight-jeans` (A, `JEAN-BLU-30`, `JEAN-BLU-32`), `white-ceramic-mug` (B, `MUG-WHT-350`), `scented-candle` (B, `CANDLE-LAV`); coupons `WELCOME10` (PLATFORM, PERCENT 1000 bps, min spend 100 000, 1 per user) and `VENDORA5` (VENDOR A, PERCENT 500 bps), valid 2026-01-01 → 2030-12-31. Products and variants are upserted one by one, so new seed rows also reach an older seeded DB.
- Money: paired `*_amount BigInt` + `*_currency Currency` (or a row-level `currency`). Never float. Prisma returns `bigint`; convert at the repository boundary with `toMoney(amount, currency)` → `@repo/core` Money (throws `money.error.overflow` beyond 2^53 − 1) and `toDbAmount(money)` → `bigint`, both exported from `src/money.ts`. bps, percents, counts and quantities stay `Int`. `Coupon.discountValue` is BigInt because it can hold a FIXED amount: pass it through `toMoney` only when `discountType = FIXED` (and `currency` is set). For `PERCENT` it is not money: it is **basis points** (1000 = 10%, valid range 1–10000, decided 2026-11-19 to match `commission_bps`) — compute the discount with `@repo/core` `applyBps(subtotal, Number(discountValue), rounding)`.
- Never `JSON.stringify` a raw Prisma row: `bigint` throws ("Do not know how to serialize a BigInt"). Map amounts with `toMoney` before building DTOs, API responses or `OutboxEvent.payload`.

## ⚠️ Search-index drift (read before running migrate dev)

The full-text/trigram indexes (`product_translations_search_vector_idx`,
`product_translations_name_trgm_idx`, `category_translations_name_trgm_idx`) and the
`search_vector` generated column are created by hand-written SQL in the `add_search_indexes`
migration. Prisma's `@@index` cannot express `USING GIN`, so `prisma migrate dev` /
`--create-only` will DETECT DRIFT and try to generate a migration that DROPS these indexes.
**Never apply/confirm a generated migration that drops `search_vector` or the GIN indexes.**
The same applies to the partial unique indexes `coupons_platform_code_key` and
`refunds_sub_order_id_active_key`, the partial indexes `crm_messages_due_idx`, `live_sessions_one_live_per_vendor_key`, `live_session_products_one_pinned_key`, `outbox_events_pending_idx` and the CHECK constraints (`crm_messages_source_check`, `platform_settings_crm_*_check`) (they have a `WHERE` clause Prisma can't model) — never confirm a
migration that drops them. Safe workflow: `migrate dev --create-only --name …`, delete the drift
statements from the generated SQL, then apply with `prisma migrate deploy`. Check with
`prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url "$SHADOW_DATABASE_URL" --script`:
the only expected output is the three search-index drops + `search_vector DROP DEFAULT`.
Add new search/partial-index SQL as a new hand-written migration instead. `prisma migrate deploy`
(prod path, no shadow diff) is unaffected.

## Commands

- `pnpm --filter @repo/db migrate` — migrate dev
- `pnpm --filter @repo/db seed` — idempotent seed
- `pnpm --filter @repo/db test` — vitest: seed idempotency + demo-data shape, ledger invariant, money boundary, ops-schema checks in rolled-back transactions (needs local postgres via `pnpm services:up`; `@repo/core` must be built first — `pnpm --filter @repo/core build`, or run through turbo `pnpm test`, which builds deps)
- `pnpm --filter @repo/db typecheck` — `tsc` for `src/` and `test/` (`test/tsconfig.json`); also needs `@repo/core` built
