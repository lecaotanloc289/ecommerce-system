# server — API (`@server/api`)

Backend HTTP API. NestJS 11 + Fastify, versioned `/v1`, OpenAPI exposed. Serves all roles via REST; webhooks (payment, OAuth callback) terminate here. Code in `server/src/`.
Read the root `CLAUDE.md` first — it is the constitution (Golden Rules, NEVER DO, naming, data flow, domain model, migration, testing). This file holds only API-specific context.

Future async workers (outbox dispatcher, payout cron, email sender) live **OUTSIDE** this workspace — a sibling top-level dir like `workers/<name>/` if/when added.

## Tech stack

- NestJS 11 + Fastify adapter, prefix `/v1`
- `nestjs-zod` pipe (validation from schemas in `@repo/core`; global `ZodValidationPipe`, failures → 422)
- Auth: `@nestjs/passport` 11 + `passport-google-oauth20` + `passport-facebook` + `@nestjs/jwt` 11 (v12 of both is ESM-only / Nest 12 — stay on 11 while the server is CJS on Nest 11)
- Redis: `ioredis` 5 (`RedisModule`, token `REDIS`) — refresh-token sessions, idempotency records, rate-limit counters; BullMQ later
- Errors: global `DomainErrorFilter` — every error leaves as `{ errorCode, params }` (`@repo/core` `DomainError` / `ERROR_CODES`)
- Logger: `nestjs-pino`
- Security: `@fastify/helmet`, `@fastify/cors` (credentials true), `@fastify/cookie`
- OpenAPI: `@nestjs/swagger` + `nestjs-zod` (`createZodDto`, `@ZodResponse`, `cleanupOpenApiDoc`) → `packages/sdk/openapi.json` → `@repo/sdk` (see "OpenAPI / SDK" below)
- Queue: BullMQ (Redis) for the outbox worker, payout scheduler, email sender

## Request pipeline

Controllers orchestrate only: middleware (helmet, cors, rate-limit, request-id) → `JwtAuthGuard` → `RolesGuard @Roles(...)` → interceptors (`@Idempotent()`) → `ZodValidationPipe` → controller → service. Business logic lives in services/domain. See root `CLAUDE.md` §4 (Data flow) for the worked checkout example.

## Idempotency (Golden Rule #3, roadmap D9)

`@Idempotent()` (`src/common/idempotency/idempotent.decorator.ts`) on a mutation handler behind `JwtAuthGuard` — mandatory on `/orders/checkout` and `/payments/*`. `IdempotencyModule` is global (registered in `AppModule`), so feature modules need no import.

- Header `Idempotency-Key` = client ULID (`IdempotencyKeySchema`). Missing or malformed → 400 `idempotency.error.key-required`. No `request.user` → 401 (fails closed; keys are per user).
- Redis key `idem:{userId}:{key}`; fingerprint = sha256(method + concrete URL incl. params/query + canonical JSON body with sorted keys). The body hashed is the JSON-parsed body (interceptors run before pipes).
- First request: `SET NX PX 60s` lock `{state:'processing'}` → handler → on 2xx store `{state:'completed', status, body}` for 24h (Lua compare-and-swap on the lock).
- Same key + same fingerprint while running → 409 `idempotency.error.in-progress`; after success → replay stored status + body with header `idempotent-replayed: true` (handler not called). Different fingerprint → 422 `idempotency.error.key-reused`.
- **Errors are not cached:** any thrown error (4xx `DomainError` included) or non-2xx status releases the lock, so the client can retry the same key.
- **Lock TTL is 60s, not renewed.** A handler running longer loses the lock; a concurrent retry may then execute again, and the late completion is logged (`idempotency lock expired…`) without overwriting. Same if writing the completed record fails (response still returned, logged). So money-moving writes (checkout, payments) **must also** have a DB unique constraint on the key (e.g. `Order.idempotencyKey`) — Redis alone is not the guarantee.
- An unreadable record (corrupt / older format) answers 422 key-reused rather than re-executing.
- Replay restores status + body only (no handler-set headers); handlers must return JSON-serializable values.

## Rate limit

`@fastify/rate-limit` registered by `registerRateLimit(app)` (`src/common/rate-limit.ts`, called in `main.ts` before `listen`), Redis store (keys `rl:*`), per client IP.

- **Client IP:** `clientIp()` takes the address `TRUSTED_PROXY_HOPS` (default 0 = socket peer; `fly.toml` sets 1 for the Fly edge) entries into `request.ips` (socket peer first, then X-Forwarded-For from nearest). Entries further left are client-supplied and ignored, so spoofing XFF cannot reset a bucket. Do **not** key on `request.ip`: `trustProxy: true` makes it the leftmost, spoofable XFF entry. Default `0` so a run without a proxy (local, direct internal address) never trusts a client-supplied XFF; only set it to the exact number of proxies that always sit in front of the API.
- **Buckets:** every route shares one bucket of `RATE_LIMIT_MAX` (default 100) per `RATE_LIMIT_WINDOW` (default `1m`). Sensitive handlers add `@RateLimit('strict')` (method-level; wraps Fastify `RouteConfig`): `RATE_LIMIT_STRICT_MAX` (default 20) in a bucket per method + route — currently all OAuth start/callback routes, `/auth/refresh`, `/auth/logout`, `POST /orders/checkout`, `POST /orders/:id/payments`; future payment routes must add it. `@SkipRateLimit()` exempts a handler (only `/health`, `/health/ready`).
- Over the limit → 429 `common.error.rate-limited` + `retry-after` (the hook throws a `DomainError`, which Nest's Fastify error handler routes through `DomainErrorFilter`).
- **Redis down:** the default bucket fails open (availability); strict routes fail closed (500) — they must not lose brute-force protection.
- **Known limit:** a server-side caller (storefront SSR on Workers) shares its egress IP's bucket across all its users. When SSR starts calling the API, give it an allow-list / trusted-client key instead of raising the global limit.

## Pagination

List endpoints take `PageQuerySchema` (`?cursor=<ulid>&limit=1..100`, default 20) and return `PageSchema(item)` = `{ items, nextCursor }` — both in `@repo/core`. `src/common/pagination.ts`: `cursorPageArgs(query, 'desc' | 'asc')` → `{ take: limit + 1, where: { id: { lt | gt: cursor } }, orderBy: { id } }` (spread `where` into your filter), then `toPage(rows, query)` trims the look-ahead row and sets `nextCursor` (null on the last page). Relies on ULID ids sorting by creation time.

## Catalog (public, no auth)

All routes are unauthenticated, take `?locale=vi|en` (default vi; a missing en translation falls back to vi) and only expose `ACTIVE` products of `ACTIVE` vendors — anything else is 404 (detail) or absent (lists/search). Schemas: `@repo/core/schemas/catalog`.

| Endpoint                           | Notes                                                                                                                                                                 |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ---------- | -------------------------- |
| `GET /v1/categories`               | Whole tree (`children` nested), siblings by `sortOrder`                                                                                                               |
| `GET /v1/categories/:slug`         | Category + `breadcrumb` (root→self) + direct `children`; slug of either locale; unknown → 404 `common.error.not-found`                                                |
| `GET /v1/products`                 | `categorySlug` (includes subcategories), `vendorSlug`, `currency`, `minPrice`/`maxPrice` (minor units), `sort=newest                                                  | price_asc | price_desc | rating`, cursor pagination |
| `GET /v1/products/:slug`           | Variants with `stockAvailable` (= onHand − reserved; raw counters never exposed), images, vendor card, rating summary; unknown/hidden → 404 `product.error.not-found` |
| `GET /v1/search?q=`                | See search below; same page shape as the list                                                                                                                         |
| `GET /v1/vendors/:slug`            | Shop header + one page of its products (same query as the list minus `vendorSlug`); not ACTIVE → 404 `vendor.error.not-found`                                         |
| `GET /v1/platform-settings/public` | `defaultCurrency`, `supportedCurrencies`, `maxCouponStack`                                                                                                            |

- **Pagination:** the cursor is always the last item's product id. Every sort (newest = constant key, so `id DESC`) is a keyset on `(sort_key, id DESC)` where the key is derived in SQL from the cursor product (`ProductsRepository.listVisibleIds`). The cursor product's key is read without the visibility filter, so paging survives it being hidden. Price filters/sorts without `currency` use `PlatformSettings.defaultCurrency`. Known perf limit (no migrations this wave): each page scans all visible products; add indexes / a newest fast path later. `rating` sorts by average (2 dp), unrated last.
- **Search** (`ProductsRepository.searchVisibleIds`, raw SQL via `$queryRaw` bound parameters): a product matches when any translation satisfies `search_vector @@ websearch_to_tsquery('simple', q)` (accent-sensitive; `simple` config, no stemming), OR `q <% name` (pg_trgm word similarity, typo tolerant), OR the accent-folded query is a substring of the ASCII slug (this gives unaccented Vietnamese matching; there is no `unaccent` extension and no migrations were added). Rank = ts_rank + word_similarity (+0.5 slug hit), keyset-paginated. Limits: unaccented queries only match slug text (keep slugs transliterated from the name); word order must match for the slug path.
- Rating summary comes from `reviews` (`average` null when none).

## Auth (Golden Rule #5)

| Endpoint                                      | Guard                        | Behaviour                                                                                                                                                                       |
| --------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/auth/google?app=web\|admin`          | `OAuthStartGuard`            | Sets `oauth_state` cookie (random state + app), 302 → Google                                                                                                                    |
| `GET /v1/auth/google/callback`                | `OAuthCallbackGuard`         | Checks `?state` == cookie (login-CSRF), resolves user, sets refresh cookie, 302 → `AUTH_REDIRECT_URL_WEB\|ADMIN`. Any failure → 302 there with `?error=auth.error.oauth-failed` |
| `GET /v1/auth/facebook`, `/facebook/callback` | same                         | same                                                                                                                                                                            |
| `POST /v1/auth/refresh`                       | cookie                       | Rotates the refresh cookie, returns `{ accessToken, tokenType: 'Bearer', expiresIn }`                                                                                           |
| `POST /v1/auth/logout`                        | cookie                       | Revokes the session (token family), clears cookie, 204 (idempotent)                                                                                                             |
| `GET /v1/auth/me`                             | `JwtAuthGuard`, `RolesGuard` | Current user profile + effective roles + vendorId                                                                                                                               |

- **Frontend flow:** navigate to `/v1/auth/<provider>?app=…` → land on the app's `/auth/callback` → `POST /v1/auth/refresh` (`credentials: 'include'`) → keep the access token in memory; call refresh again on 401 `auth.error.token-expired`.
- **User resolution** (`AuthService.resolveOAuthUser`, one `$transaction`): known identity → login; provider-**verified** email matching a `User` → link new `OAuthIdentity`; else create `User` + `OAuthIdentity` + `UserRole CUSTOMER` (ULIDs). Unverified emails are never linked and never stored on `User.email` (blocks pre-account-takeover). Facebook emails are always treated as unverified (Graph API gives no guarantee) — so a Facebook-only user has `User.email = null` and a later Google login with the same address creates a separate account (accepted trade-off for takeover safety; an explicit "link account" flow is future work). Emails are stored and matched lowercase — keep every writer (seed included) lowercasing.
- **Access JWT** (HS256, `JWT_ACCESS_SECRET`, `JWT_ACCESS_TTL` = 15m): `{ sub, roles, vendorId? }` from `UserRole` rows; vendor roles count only while the vendor is `ACTIVE`; `vendorId` = oldest active vendor role. Roles are re-read on every refresh.
- **Refresh JWT** (HS256, `JWT_REFRESH_SECRET`, `JWT_REFRESH_TTL` = 30d): `{ sub, fid, jti }` in cookie `refresh_token` (HttpOnly, Secure, SameSite=Lax, Path=`/v1/auth`). State in Redis, no DB table: `auth:rt:family:<fid>` = `{ userId, current, prev, rotatedAt }` (sha256 hashes), TTL slides on rotation. Rotation is an atomic Lua compare-and-swap. Presenting `prev` within `REFRESH_REUSE_GRACE_MS` (10s) is a benign concurrent refresh (two tabs, SSR + client, StrictMode): it gets an access token but no new cookie, and the family survives (logged at info; the window uses the Redis server clock). Any other non-current token deletes the family (reuse detection → that session is logged out). The DB lookup for the access token runs _before_ the swap, so a DB failure never strands the client with a rotated-away cookie. Limit: if a successful refresh response is _lost in transit_ and the client retries within 10s, it keeps the stale cookie and is logged out at its next refresh — frontends should single-flight refresh calls (one in-flight refresh shared by all callers).
- **Protecting routes:** import `AuthModule`, then `@UseGuards(JwtAuthGuard, RolesGuard) @Roles('VENDOR_OWNER')`; read the caller with `@CurrentUser() user: AuthUser` (`{ id, roles, vendorId? }`). `RolesGuard` fails closed — a guarded route without `@Roles` is 403; use `@Roles(...ALL_ROLES)` for "any signed-in user".
- **Known limits:** access tokens stay valid until expiry (≤ 15m) after logout, family revocation, vendor suspension or role removal (no denylist / per-user session index yet) — services must re-check vendor status/ownership in the DB before destructive vendor or payout actions rather than trusting `req.user.vendorId` alone. The refresh cookie is always `Secure` (Golden Rule #5): Chrome/Firefox accept it on `http://localhost`, Safari may not — use Chrome for local login. SameSite=Lax means the API must be same-site with the web/admin origins in prod (e.g. `api.example.com` + `example.com`), otherwise the refresh cookie isn't sent. `TokenResponse` / `MeResponse` live in `@repo/core/schemas/me`; `src/auth/auth.schemas.ts` keeps only the server-internal schemas (token claims, `AuthUser`, OAuth profile).

## Me: profile + addresses (`src/me/`)

All routes `@Roles('CUSTOMER')`; ownership only via `req.user.id` (another user's address → 404 `address.error.not-found`, never 403). POST/PATCH carry `@Idempotent()`.

| Endpoint                            | Behaviour                                                                                                          |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `PATCH /v1/me`                      | `{ name?, primaryLocale? }` (non-empty) → `MeResponse`. Email/roles/avatar are not editable                        |
| `GET /v1/me/addresses`              | Array of `Address`, default first then newest                                                                      |
| `POST /v1/me/addresses`             | `AddressInput` (country defaults `VN`) → 201. First address is always default; `isDefault: true` moves the default |

## Cart (`src/cart/`)

All routes `@Roles('CUSTOMER')`, scoped to `req.user.id`; shapes in `@repo/core/schemas/cart`. Prices are never stored — every read joins the current variant price. `?locale=vi|en` (default vi) picks the product name/slug (falls back to any translation).

| Endpoint                                   | Behaviour                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/cart`                             | Lines grouped by vendor (oldest line first): `unitPrice`, `lineTotal`, `stockAvailable`, `unavailable` (product not ACTIVE or vendor not ACTIVE). Per-group `subtotals` are per currency over available lines; `hasMixedCurrency` flags a mixed cart. Does not create a Cart row.                                                                                                                     |
| `PUT /v1/cart/items/:variantId {quantity}` | `@Idempotent`. Sets the quantity; `0` removes (also works for unavailable lines). Unknown variant → 404 `product.error.variant-not-found`; product/vendor not ACTIVE → 409 `product.error.not-available`; over stock → 409 `cart.error.quantity-exceeds-stock`.                                                                                                                                       |
| `DELETE /v1/cart/items/:variantId`         | `@Idempotent`. Removes the line; absent line is a no-op. Returns the cart.                                                                                                                                                                                                                                                                                                                            |
| `POST /v1/cart/merge {items[]}`            | `@Idempotent`. Guest-cart merge: quantities add to existing lines (duplicates summed), clamped to `stockAvailable`; a merge never lowers an existing line; unknown/unsellable variants are dropped. Returns `{ cart, adjustments[] }` (`CLAMPED` / `UNAVAILABLE`). Same key replays; a **new key adds the quantities again**, so the client calls merge once after login, then clears the guest cart. |
| `GET /v1/cart/shipping-options`            | Active `ShippingMethod`s per vendor present in the cart (sellable lines only), `{ groups: [{ vendorId, methods }] }`.                                                                                                                                                                                                                                                                                 |

Lazy cart creation is `createMany({ skipDuplicates })` (INSERT … ON CONFLICT DO NOTHING) on the unique `userId` then a read — race-safe, unlike Prisma `upsert` which can still raise P2002; the number of distinct lines is capped at `MAX_CART_LINES` (100, `cart.error.too-many-lines`); `stockAvailable` is advisory, checkout re-checks stock atomically; lowering a line is always allowed; merge locks the cart row (`SELECT … FOR UPDATE`) in its transaction. Tests: `test/integration/cart.spec.ts`.

## Orders: checkout + customer orders (`src/orders/`)

All routes `@Roles('CUSTOMER')`, scoped to `req.user.id`; another user's order is 404 `order.error.not-found` (never 403). Shapes in `@repo/core/schemas/order` + `checkout`.

| Endpoint                       | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/orders/checkout`     | `@Idempotent()` + `@RateLimit('strict')`, body `Checkout` → 201 `Order` (status AWAITING_PAYMENT, one PENDING payment without session). Transaction below.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `GET /v1/orders`               | `OrderSummaryPage`, newest first, cursor pagination (`itemCount` = Σ quantities).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `GET /v1/orders/:id`           | `Order` with sub-orders + items (snapshots).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `GET /v1/orders/:id/payment`   | `PaymentSession` of the latest attempt. **202** while that attempt is PENDING and `redirectUrl` is null (worker not done — poll 1s, ≤ 30s); **200** once `redirectUrl` is set or the attempt is no longer PENDING (read `status`). Same body shape for both; no error code.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `POST /v1/orders/:id/cancel`   | `@Idempotent()`, → 200 `Order` (CANCELLED). Only while every sub-order is AWAITING_PAYMENT, else 409 `order.error.invalid-status-transition`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `POST /v1/orders/:id/payments` | `@Idempotent()` + strict, body `PaymentRetry {provider?}` → 201 `PaymentSession` (new attempt, PENDING, no session yet — poll as above). Order AWAITING_PAYMENT (else 409 invalid-status-transition), `paymentDeadlineAt` not passed and latest attempt FAILED, PENDING past `expiresAt`, or PENDING still without `redirectUrl` 2 min (`SESSION_CREATION_TIMEOUT_MS`) after creation (else 409 `payment.error.retry-not-allowed` `{reason: 'deadline-passed' \| 'payment-pending'}`). The provider must support the order currency (else 422 `payment.error.provider-currency-unsupported`). The expired/stuck PENDING attempt becomes FAILED; `attemptNo + 1`, amount = order grand total, provider defaults to the previous one; outbox `payment.requested`. |

`POST /v1/orders/:orderId/sub-orders/:id/confirm-received` (customer confirms receipt) is documented under "Fulfilment + wallet" below.

**Checkout transaction** (`CheckoutService`, one interactive `$transaction`, READ COMMITTED + row locks, 15s timeout; any error rolls back everything):

1. `PlatformSettings` (missing → 500) and the buyer (`primaryLocale`).
2. Variants + product + vendor + categories. Unknown → 404 `product.error.variant-not-found`; product or vendor not ACTIVE → 409 `product.error.not-available`.
3. One currency for every line, and in `supportedCurrencies` (D6) → else 422 `checkout.error.currency-mismatch`. The provider must charge that currency (`providerSupportsCurrency`: VNPay VND only, Stripe VND/USD) → else 422 `payment.error.provider-currency-unsupported`.
4. Address must be the buyer's (404 `checkout.error.address-not-found`) → `ShippingAddressSnapshot` JSON on each sub-order.
5. Group by vendor (first-appearance order). `shippingMethodIds` must give exactly one active method per vendor of the order, owned by it and in the order currency: unknown / inactive / foreign / second-for-a-vendor → 422 `checkout.error.shipping-method-invalid {shippingMethodId}`; vendor without one → 422 `…-missing {vendorId}`.
6. Coupons: `SELECT … FOR UPDATE` (id order) on the coupon rows matching the codes (platform: `vendor_id IS NULL`; vendor: `vendor_id` among the order's vendors), then count redemptions (total + this user). A code resolves to the **active platform coupon** with that code if there is one (platform codes win, vendors cannot shadow them), otherwise to every vendor coupon with that code of the vendors in the order; nothing → 404 `coupon.error.not-found {code}`. A coupon in another currency → 422 `checkout.error.currency-mismatch {code}`. Eligibility/limits/stacking are `priceOrder`'s (`coupon.error.*`); when a code matches several vendors' coupons, any ineligible one rejects the whole checkout.
7. Commission bps per line via `resolveCommissionBps` (vendor override → lowest category override → platform), then `priceOrder` (D5-D8).
8. Reserve stock (D4) line by line **in variant-id order** (deadlock-free between concurrent checkouts): `UPDATE … SET stock_reserved = stock_reserved + qty WHERE id = ? AND stock_on_hand - stock_reserved >= qty`; 0 rows → 409 `checkout.error.out-of-stock {variantId}` (earlier reservations roll back too).
9. Insert `Order` (`idempotencyKey` = header key, `paymentDeadlineAt` = now + `paymentTimeoutMinutes`), `SubOrder`s (`discountAmount` = vendor discount, `platformDiscountAmount`, `commissionAmount` from the pricing result), `OrderItem`s (title in the buyer's `primaryLocale`, fallback vi; attributes; unit price; line total), `CouponRedemption`s (all carry `orderId`; vendor ones also `subOrderId`), `Payment {PENDING, attemptNo 1, provider, amount = grandTotal}`, outbox `order.created` + `payment.requested`; delete the purchased variants' lines from the server cart (whole line, even if the cart held more than was bought — the body, not the cart, drives checkout). **No ledger rows** (D3: escrow IN is written by the payment confirmation, T3.1).

- **Idempotency backstop:** before the transaction, and again after **any** failure of it (a concurrent same-key winner shows up as P2002 on `orders.idempotency_key`, or as out-of-stock on the unit it just reserved), the order with that key is looked up: same user + same items/shipping methods/provider → that order is returned (201); another user or a different body → 422 `idempotency.error.key-reused` (address and coupon codes are not compared). Known limit: the key is unique globally, not per user (fixing it needs a migration to `(customer_id, idempotency_key)`); random ULID keys make collisions impractical.
- **Grand total 0** (free shipping + 100% coupons) is allowed and still creates a PENDING payment of 0 + `payment.requested`: the worker (T2.2) must not open a provider session for 0 and should confirm it through the same path as a webhook (T3.1), so stock commit and ledger stay in one place.
- **Outbox** (`aggregateType = 'order'`, `aggregateId = orderId`; payload schemas in `@repo/core/schemas/outbox`, ids only): `order.created {orderId, customerId}`, `payment.requested {orderId, paymentId, provider, attemptNo}`, `order.cancelled {orderId, customerId, reason: 'CUSTOMER' | 'PAYMENT_EXPIRED'}`; fulfilment adds `sub-order.shipped` / `sub-order.delivered {orderId, subOrderId, customerId}` and `sub-order.completed {orderId, subOrderId, vendorId}`.

**Cancellation contract** — `cancelOrder(tx, orderId, reason)` in `order-cancellation.ts`, shared with the payment-expiry job (T3.2 mirrors it; returns `'cancelled' | 'not-found' | 'not-cancellable'` without writing in the last two cases): lock the order row (`SELECT … FOR UPDATE` — the payment confirmation must take the same lock first); require every sub-order AWAITING_PAYMENT; sub-orders → CANCELLED + `cancelledAt` with `WHERE status = 'AWAITING_PAYMENT'` (count mismatch throws → rollback); release `stock_reserved` per variant in id order, clamped at 0; delete the order's CouponRedemptions; PENDING payments → FAILED; `orders.status` = `deriveOrderStatus(...)`; outbox `order.cancelled`. Ownership is checked by the caller; it does not look at `paymentDeadlineAt` — the expiry job selects overdue orders itself and passes `PAYMENT_EXPIRED`. The clamp at 0 is only a safety net (the status guard prevents a double release).

**Contracts for later tasks:** the T2.2 worker writes `Payment.redirectUrl` / `expiresAt` only `WHERE status = 'PENDING'` (a retry or cancel may have failed the attempt meanwhile). T3.1 confirmation must lock the order row first and route a CONFIRMED webhook for an attempt that is already FAILED (replaced by a retry, or order cancelled) to the refund path.

Tests: `test/integration/orders.spec.ts` (single + two-vendor money, out-of-stock rollback, concurrent last unit, idempotency replay + DB backstop, coupon limit, shipping validation, client prices ignored, cancel, 404 for others, payment session 202/200, retry rules).

## Vendor catalog (`src/vendor/`)

All routes `@Roles('VENDOR_OWNER','VENDOR_STAFF')`; the vendor comes ONLY from `req.user.vendorId` (no vendorId in the JWT -> 403 `vendor.error.not-active`). Every query is scoped by it, so another vendor's product / variant / shipping method is 404. Every write runs in a `$transaction` that first re-reads `vendors.status` (`SELECT ... FOR SHARE`, `assertVendorActive`): SUSPENDED -> 403 `vendor.error.suspended`, other non-ACTIVE -> 403 `vendor.error.not-active` (a stale JWT cannot bypass it). Reads stay open. `VendorMembershipGuard` re-checks in the DB that the caller still holds a vendor role on `vendorId` (a revoked staff member loses access immediately, not after the 15m JWT). PUT on a BLOCKED product is refused (409 `product.error.blocked`). Mutations carry `@Idempotent()`. Shapes: `@repo/core/schemas/product-admin` (`VendorProduct`, `VendorProductPage`, `VendorProductVariant`, `ProductUpsert`, `VariantStockUpdate`) + `shipping-method`.

| Endpoint                                                                   | Behaviour                                                                                                                                                                                                                                                         |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/vendor/products?status&cursor&limit`                              | Own products newest first (`VendorProductPage`; `name` = vi name, `stockOnHand` = sum)                                                                                                                                                                            |
| `POST /v1/vendor/products`                                                 | `ProductUpsert` -> 201 DRAFT `VendorProduct`; variant/image `id` not allowed                                                                                                                                                                                      |
| `GET /v1/vendor/products/:id`                                              | Raw vi + en translations, variants with `stockOnHand` + `stockReserved`, `status`, `blockedReason`                                                                                                                                                                |
| `PUT /v1/vendor/products/:id`                                              | Full replace (translations, variants, images, categories); body `status` is **ignored** (status moves only via publish / archive)                                                                                                                                 |
| `POST /v1/vendor/products/:id/publish`                                     | -> ACTIVE. Needs a vi name + at least one variant with EVERY variant priced > 0 (stricter than the roadmap: a 0-priced variant would sell for free) (else 422 `product.error.not-publishable`); BLOCKED -> 409 `product.error.blocked`; already ACTIVE is a no-op |
| `POST /v1/vendor/products/:id/archive`                                     | -> ARCHIVED (BLOCKED -> 409 `product.error.blocked`)                                                                                                                                                                                                              |
| `PATCH /v1/vendor/variants/:id/stock {stockOnHand}`                        | Absolute on-hand count                                                                                                                                                                                                                                            |
| `GET/POST /v1/vendor/shipping-methods`, `PUT /:id`, `POST /:id/deactivate` | Own methods incl. inactive; currency must be supported; deactivate only stops new checkouts                                                                                                                                                                       |

- **Slugs / skus:** `(locale, slug)` and `sku` are globally unique -> 409 `common.error.conflict {field}` (pre-checked in the transaction; a lost race on the unique index is mapped to the same 409). Both translations (vi + en) are required by `ProductUpsertSchema`.
- **Variants** are matched by `id`, else by `sku` within the product. A variant missing from the payload is deleted only if no `OrderItem` and no `CartItem` references it, otherwise 409 `product.error.variant-in-use` (the vendor sets stock to 0 instead; there is no per-variant archive).
- **Stock:** never a blind overwrite. PUT and PATCH use `UPDATE ... WHERE stock_reserved <= :new` (`updateMany`), the same row-lock semantics as checkout's reservation `UPDATE`, so a concurrent reservation cannot be undercut; 0 rows -> 409 `product.error.stock-below-reserved {stockReserved}` (and the whole PUT rolls back).
- **Prices:** minor units; currency must be in `PlatformSettings.supportedCurrencies` (else 422 `common.error.validation-failed`), all variants share the product currency. **`Product.basePriceAmount` is always `MIN(variant priceAmount)`** (currency = product currency), recomputed in the same transaction on create / PUT, because the public catalog filters/sorts on it while cart/checkout charge the variant price; the client-sent `basePrice.amount` is ignored (only its currency is used). Variant prices change only through PUT.
- **Images:** array order = display order (`sortOrder` = index); `{ key }` is checked with `StorageService.assertOwnedKey(key, { type: 'vendor', vendorId })` and stored as `publicUrl(key)` in `ProductImage.url` (what public catalog reads return); `{ id }` keeps an own image (foreign id -> 404 `common.error.not-found`); images not listed are deleted (DB rows only, objects stay in S3). `Product.primaryImageUrl` = the first image (lowest `sortOrder`) or null.
- **Search:** `product_translations.search_vector` is a _generated_ column (no trigger, nothing to maintain in the app); a published product is searchable immediately and a rename is picked up on PUT.
- Tests: `test/integration/vendor-catalog.spec.ts`.

## Fulfilment + wallet (`src/vendor-orders/`, T3.3)

Vendor routes reuse the vendor-catalog scope: `@Roles('VENDOR_OWNER','VENDOR_STAFF')` + `VendorMembershipGuard`, vendor ONLY from `req.user.vendorId` (`requireVendorId`), writes re-check `vendors.status` (`assertVendorActive`, SUSPENDED → 403 `vendor.error.suspended`), mutations `@Idempotent()`. Vendors only see **paid** sub-orders (`VendorSubOrderStatus` = PAID..COMPLETED + REFUNDED): AWAITING_PAYMENT and CANCELLED ones — and another vendor's — are 404 `sub-order.error.not-found` / absent from lists. Shapes: `@repo/core/schemas/order` (`VendorSubOrder`, `VendorSubOrderPage`, `VendorSubOrderQuery`, `SubOrderShip`) + `wallet` (`VendorWallet`, `LedgerEntryPage`).

| Endpoint                                                        | Behaviour                                                                                                                                                                                                                                                   |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/vendor/sub-orders?status&cursor&limit`                 | Own paid sub-orders newest first (`VendorSubOrderPage`); `status` must be a `VendorSubOrderStatus` (else 422)                                                                                                                                               |
| `GET /v1/vendor/sub-orders/:id`                                 | `VendorSubOrder`: items, shipping address snapshot (customer contact = `shippingAddress.recipientName` / `phone`, never the user profile/email), `total` (paid_i), `commission`, `net` = subtotal + shipping − vendorDiscount − commission (D7)             |
| `POST /v1/vendor/sub-orders/:id/accept`                         | PAID → PROCESSING (no outbox event)                                                                                                                                                                                                                         |
| `POST /v1/vendor/sub-orders/:id/ship {carrier, trackingNumber}` | PROCESSING → SHIPPED, sets `carrier`, `trackingNumber`, `shippedAt`; outbox `sub-order.shipped`                                                                                                                                                             |
| `POST /v1/vendor/sub-orders/:id/deliver`                        | SHIPPED → DELIVERED, sets `deliveredAt`; outbox `sub-order.delivered`                                                                                                                                                                                       |
| `POST /v1/orders/:orderId/sub-orders/:id/confirm-received`      | Customer (`OrdersController`): SHIPPED \| DELIVERED → COMPLETED, sets `completedAt` (+ `deliveredAt` if still null); outbox `sub-order.completed`; returns the `Order`                                                                                      |
| `GET /v1/vendor/wallet`                                         | `VENDOR_OWNER` only. `{ id, vendorId, balance, pending[] }`: `balance` = `Wallet.balance` (released payouts); `pending` = Σ net of own sub-orders in PAID..COMPLETED with `payoutReleasedAt IS NULL`, one Money per currency (alphabetical; `[]` when none) |
| `GET /v1/vendor/ledger?cursor&limit`                            | `VENDOR_OWNER` only. Own `LedgerEntry` rows with `account = VENDOR_WALLET AND vendor_id = me`, newest first; escrow / revenue lines never leave                                                                                                             |

**State machine** — `@repo/core` `SUB_ORDER_TRANSITIONS` / `canTransition(from, to, actor)` / `assertTransition` (`packages/core/src/orders/sub-order-state.ts`), the one table every writer of `SubOrder.status` must respect:

| From                                    | To         | Actor                                  |
| --------------------------------------- | ---------- | -------------------------------------- |
| AWAITING_PAYMENT                        | PAID       | SYSTEM (payment confirmation, T3.1)    |
| AWAITING_PAYMENT                        | CANCELLED  | CUSTOMER, SYSTEM (expiry)              |
| PAID                                    | PROCESSING | VENDOR                                 |
| PROCESSING                              | SHIPPED    | VENDOR                                 |
| SHIPPED                                 | DELIVERED  | VENDOR                                 |
| SHIPPED                                 | COMPLETED  | CUSTOMER                               |
| DELIVERED                               | COMPLETED  | CUSTOMER, SYSTEM (auto-complete, T3.2) |
| PAID / PROCESSING / SHIPPED / DELIVERED | REFUNDED   | PLATFORM (T3.5)                        |

COMPLETED, REFUNDED and CANCELLED are terminal. Anything else → 409 `order.error.invalid-status-transition {from, to}`.

**Transition contract** — `transitionSubOrder(tx, ref, target)` (`src/orders/sub-order-transition.ts`; used by the vendor service and `OrdersService.confirmReceived`; the T3.2 auto-complete job lives in `workers/` and cannot import it, so it mirrors these steps with `assertTransition('DELIVERED', 'COMPLETED', 'SYSTEM')`). One `$transaction` per request; the caller first resolves the sub-order **scoped** to the vendor / customer, then: lock the ORDER row (`SELECT … FOR UPDATE`, same lock order as checkout / cancel / payment confirmation) → VENDOR moves `assertVendorActive` → re-read the status under the lock and `assertTransition` → `UPDATE … WHERE id = ? AND status = <from>` (0 rows → 409) + timestamps → `orders.status = deriveOrderStatus(all sub-orders)` → outbox (`aggregateType = 'order'`, `aggregateId = orderId`). Two concurrent accepts serialise on the order lock: one 200, the other 409. Wallet / ledger reads re-check in the DB that the caller holds `VENDOR_OWNER` on `vendorId` (a user can own one vendor and be staff of another). Tests: `test/integration/vendor-fulfilment.spec.ts`.

## Storage / uploads (roadmap D13)

`StorageModule` (`src/storage/`) exports `StorageService`; import it in a feature module to validate or read keys. AWS SDK v3 (`@aws-sdk/client-s3` + `s3-request-presigner`), `forcePathStyle` locally. Local S3 = RustFS (compose service `s3`, ports 9000/9001, creds `rustfsadmin`; Docker Hub `minio/minio` is no longer pullable) plus the one-shot `s3-init` job (`docker/s3-init.sh`) that creates `kyc` (private) and `media` (public read).

- **Env** (`env.ts`): `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (required), `S3_FORCE_PATH_STYLE` (default true; set false for R2 virtual-host style if desired), `S3_BUCKET_KYC` (`kyc`), `S3_BUCKET_MEDIA` (`media`), `MEDIA_PUBLIC_BASE_URL` (default `http://localhost:9000/media`; `publicUrl` = base + `/` + key, so locally the path reads `/media/media/vendors/…` — the key itself starts with `media/`).
- **`POST /v1/uploads/presign`** (`UploadsController`, `JwtAuthGuard` + `RolesGuard`, body `PresignRequest`, returns `PresignResponse`): `kyc` needs `CUSTOMER` (key `kyc/{userId}/{ulid}.{ext}`, jpeg/png/webp/pdf); `product-image` / `vendor-logo` need `VENDOR_OWNER|VENDOR_STAFF` with `vendorId` from the token (key `media/vendors/{vendorId}/{ulid}.{ext}`, jpeg/png/webp). Max 10 MB, URL valid 5 min. Errors: `upload.error.content-type-not-allowed` (422), `upload.error.too-large` (413), `common.error.forbidden`. No `@Idempotent()`: presigning writes no state (a retry just returns another unused key). Default rate-limit bucket.
- **Content-Type and size are enforced by S3, not by us:** the PUT is signed with `content-type` and `content-length` as signed headers, so a PUT with a different type or byte length gets 403 (verified against RustFS). The client must send `headers` from the response and a body of exactly the declared `size`. We do not inspect the bytes (no magic-number sniffing / virus scan).
- **`StorageService`:** `presignPut(purpose, owner, contentType, size)`, `presignGet(key)` (kyc keys only, 60s TTL — authorise platform staff in the caller), `publicUrl(key)` (media keys only), `assertOwnedKey(key, owner)` → returns the key or throws `upload.error.invalid-key`. `owner` = `{ type: 'user', userId }` for kyc keys, `{ type: 'vendor', vendorId }` for media keys (always from `req.user`). It checks owner + shape only (media keys: images only), not the exact purpose and not that the object exists — HEAD it if that matters. Signed `content-length` is verified on RustFS only; smoke-test on R2 before prod. In production `S3_ENDPOINT` / `MEDIA_PUBLIC_BASE_URL` must not be localhost (env refine). **Any feature that persists a client-echoed key (vendor application, product images, logo) must call `assertOwnedKey` first.**
- The S3 client is lazy (no connection at construction), so `openapi:export` needs no S3 stub. Unit tests mock the presigner (`test/storage/`, `test/http/uploads.http.spec.ts`); there is no Testcontainers S3 test (the harness only starts Postgres + Redis).

## Vendor applications (`src/vendor-applications/`, T2.3)

One module, two controllers. The applicant is always `req.user.id`; no client `userId`/`vendorId`. KYC numbers are never logged. Shapes in `@repo/core/schemas/vendor`.

| Endpoint                                                                | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/vendor-applications`                                          | `CUSTOMER`, `@Idempotent()` + strict rate limit, body `VendorApplicationCreate` → 201 `VendorApplicationListItem` (PENDING, **masked**: `@Idempotent()` caches the response body in Redis for 24h, so KYC numbers must not be in it; read the full row via `/me`). The two keys must differ. Both KYC keys go through `storage.assertOwnedKey(key, {type:"user"})` (else 422 `upload.error.invalid-key`) and are stored in `business_license_url` / `national_id_url`. PENDING exists → 409 `vendor.error.application-already-pending`; caller already owns a vendor → 409 `common.error.conflict`. The user row is locked (`FOR UPDATE`) so concurrent submits cannot both be PENDING. Re-applying after REJECTED is allowed. |
| `GET /v1/vendor-applications/me`                                        | `{ latest, history }` (newest first, max 20; `latest` = `history[0]`). Own data, unmasked.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `GET /v1/platform/vendor-applications?status=&cursor=&limit=`           | `PLATFORM_STAFF                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | PLATFORM_ADMIN`; cursor page of `VendorApplicationListItem` — taxId / nationalIdNumber / bankAccountNumber masked to the last 4 chars (`\*` fill). |
| `GET /v1/platform/vendor-applications/:id`                              | Full application (each read is logged with reviewer + application ids, no values) + `businessLicenseUrl` / `nationalIdUrl` = presigned GET URLs (`presignGet`, 60s).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `POST /v1/platform/vendor-applications/:id/approve {slug, displayName}` | `@Idempotent()`. Transaction below → `VendorApplicationReviewResult` (masked row + `vendorId`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `POST /v1/platform/vendor-applications/:id/reject {reason}`             | `@Idempotent()`. REJECTED + reason + reviewer + reviewedAt + outbox `vendor.application.rejected`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

**Self-review:** approve/reject by the applicant themself (staff are also customers) → 403 `common.error.forbidden`. Masking shows at most half of a short value (min(4, len/2) trailing chars). No DB constraint yet backs "one PENDING per user" / "one vendor per owner" (service locks only; a partial unique index needs a migration).

**Approval transaction:** `SELECT … FROM vendor_applications WHERE id = $1 FOR UPDATE` → not found 404 `common.error.not-found`, not PENDING 409 `vendor.error.application-not-pending` (so approving twice / concurrently yields exactly one vendor) → slug taken or applicant already owns a vendor → 409 `common.error.conflict` (P2002 on the slug index maps to the same) → create Vendor ACTIVE + Wallet (`PlatformSettings.defaultCurrency`, balance 0) + `UserRole VENDOR_OWNER` (with vendorId) → application APPROVED + `reviewedById` + `reviewedAt` → outbox `vendor.application.approved` {applicationId, vendorId, userId} (`aggregateType` `vendor-application`). The applicant sees `VENDOR_OWNER` + `vendorId` from their next access-token refresh (roles re-read then; the current access token stays stale for ≤ 15m). Tests: `test/integration/vendor-applications.spec.ts`.

## OpenAPI / SDK

- `src/openapi/openapi.ts` — `buildOpenApiDocument(app)` (DocumentBuilder + `cleanupOpenApiDoc`; exports `BEARER_AUTH`, `REFRESH_COOKIE_AUTH` scheme names). Only with `NODE_ENV=development`, `main.ts` serves Swagger UI at `/docs` and the raw spec at `/v1/openapi.json`.
- `pnpm --filter @server/api openapi:export` (`scripts/export-openapi.ts`, run via ts-node with `tsconfig.scripts.json`) builds the real `AppModule` with stubbed `PrismaService` + `REDIS` and a fixed dummy env — no Postgres/Redis needed — and writes `packages/sdk/openapi.json` with sorted keys (deterministic). Root `pnpm sdk:generate` = export + `openapi-typescript` + SDK build; CI fails on drift.
- **Every new route must declare its schemas so it reaches the SDK:** DTO classes via `createZodDto(Schema)`, DTO-typed `@Body/@Query/@Param`, `@ZodResponse({ status, type })` for the response (a global `ZodSerializerInterceptor` parses it), `@ApiTags/@ApiOperation`, `@ApiBearerAuth(BEARER_AUTH)` on guarded routes; then run `pnpm sdk:generate` and commit. Details: `packages/sdk/CLAUDE.md`. Auth DTOs: `src/auth/auth.dto.ts`; health: `src/health/health.dto.ts`.
- A new module that needs a live resource at construction (queue, S3 client, …) must also be stubbed in `scripts/export-openapi.ts`, or the export will try to connect.

Under `test/**` only the `no-unsafe-*` and `unbound-method` rules are off (Jest mocks are `any`, `expect(obj.method)` is idiomatic). `tsconfig.json` extends `../packages/config/...` by relative path — typescript-eslint does not realpath the `@repo/config` symlink, so the package-name form breaks the `extends` chain.

Tests live in `server/test/` (excluded from the build). `jest.config.js` has two projects: **unit** (everything except `test/integration/` — `auth/`, `common/`, `config/`, `http/` in-process Fastify `inject` with mocked Prisma; no Docker) and **integration** (`test/integration/`, needs Docker; CI runners have it). `pnpm --filter @server/api test -- --selectProjects unit` skips Docker; selecting only unit files does too.

### Integration harness (`test/support/`)

- **Containers:** `global-setup.ts` starts ONE Postgres 16 + ONE Redis 7 per `jest` run (only if an integration spec is selected), runs `prisma migrate deploy` (packages/db/prisma) into a template DB, and clones `worker_N` per Jest worker; each worker also gets Redis logical DB N. `integration-env.ts` points `DATABASE_URL`/`REDIS_URL` at the worker's pair. Chosen over a container set per file: start-up + migrations cost ~5s once instead of per file (whole integration suite ≈ 8s wall). Never touches the shared local Postgres/Redis.
- **`createTestApp({ env?, imports? })`** → `TestApp { app, db, redis, env, authHeader(user), signAccessToken(user, roles, vendorId?), reset(), close() }`: the real `AppModule` on Fastify with the same plugins as `main.ts` (keep in sync), pino silenced, rate limits raised to 100000 (override via `env`). It starts from an empty DB (`reset()` = TRUNCATE all tables + FLUSHDB; it refuses to run on a non-`worker_N` database). Call `t.reset()` in `beforeEach` when tests must not see each other's rows. Test-only controllers go in a module passed via `imports` (that module imports `AuthModule` to use `JwtAuthGuard`).
- **Auth:** `await t.authHeader(user)` → `{ authorization: 'Bearer …' }` signed by the real `TokenService` from the user's DB roles (vendor roles only while the vendor is ACTIVE). `t.signAccessToken(user, roles, vendorId?)` crafts arbitrary claims (stale vendorId, revoked role).
- **Factories** (`factories.ts`, re-exported from `test/support`): `makeUser(db, { roles?, vendorId?, email?, … })`, `makeVendor(db, { status?, ownerId?, currency?, commissionBpsOverride? })` → `{ vendor, owner, wallet }` (owner gets `VENDOR_OWNER`), `makeCategory`, `makeProduct(db, { vendorId, status?, currency?, price?, variants?: [{ price?, stockOnHand?, stockReserved?, sku? }], categoryIds? })` (vi/en translations, variants, image), `makeShippingMethod(db, { vendorId, price?, … })`, `makeAddress(db, { userId, isDefault? })`, `makeCoupon(db, { scope?, vendorId?, code?, discountType?, discountValue?, maxRedemptions?, perUserLimit?, … })` (default PLATFORM PERCENT 10%, valid yesterday → +1 year), `makePlatformSettings(db, overrides)`. Amounts are integer minor units; ids are monotonic ULIDs (creation order = id order).
