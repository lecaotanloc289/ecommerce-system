# server — API (`@server/api`)

Backend HTTP API. NestJS 11 + Fastify, versioned `/v1`, OpenAPI exposed. Serves all roles via REST; webhooks (payment, OAuth callback) terminate here. Code in `server/src/`.
Read the root `CLAUDE.md` first — it is the constitution (Golden Rules, NEVER DO, naming, data flow, domain model, migration, testing). This file holds only API-specific context.

Future async workers (outbox dispatcher, payout cron, email sender) live **OUTSIDE** this workspace — a sibling top-level dir like `workers/<name>/` if/when added.

## Tech stack

- NestJS 11 + Fastify adapter, prefix `/v1`
- `nestjs-zod` pipe (validation from schemas in `@repo/core`; global `ZodValidationPipe`, failures → 422)
- Auth: `@nestjs/passport` 11 + `passport-google-oauth20` + `passport-facebook` + `@nestjs/jwt` 11 (v12 of both is ESM-only / Nest 12 — stay on 11 while the server is CJS on Nest 11)
- Redis: `ioredis` 5 (`RedisModule`, token `REDIS`) — refresh-token sessions, idempotency records, rate-limit counters, live realtime (pub/sub, chat stream, presence); BullMQ later
- Errors: global `DomainErrorFilter` — every error leaves as `{ errorCode, params }` (`@repo/core` `DomainError` / `ERROR_CODES`)
- Logger: `nestjs-pino`
- Security: `@fastify/helmet`, `@fastify/cors` (credentials true), `@fastify/cookie`
- OpenAPI: `@nestjs/swagger` + `nestjs-zod` (`createZodDto`, `@ZodResponse`, `cleanupOpenApiDoc`) → `packages/sdk/openapi.json` → `@repo/sdk` (see "OpenAPI / SDK" below)
- Queue: BullMQ (Redis) for the outbox worker, payout scheduler, email sender

## Request pipeline

Controllers orchestrate only: middleware (helmet, cors, rate-limit, request-id) → `JwtAuthGuard` → `RolesGuard @Roles(...)` → interceptors (`@Idempotent()`) → `ZodValidationPipe` → controller → service. Business logic lives in services/domain. See root `CLAUDE.md` §4 (Data flow) for the worked checkout example.

## Idempotency (Golden Rule #3, roadmap D9)

`@Idempotent()` (`src/common/idempotency/idempotent.decorator.ts`) on a mutation handler behind `JwtAuthGuard` — mandatory on `/orders/checkout` and customer payment routes (`/orders/:id/payments`); provider webhooks (`/payments/webhook/*`) are exempt — no user, no key; the confirmation transaction is idempotent instead. `IdempotencyModule` is global (registered in `AppModule`), so feature modules need no import.

- Header `Idempotency-Key` = client ULID (`IdempotencyKeySchema`). Missing or malformed → 400 `idempotency.error.key-required`. No `request.user` → 401 (fails closed; keys are per user).
- Redis key `idem:{userId}:{key}`; fingerprint = sha256(method + concrete URL incl. params/query + canonical JSON body with sorted keys). The body hashed is the JSON-parsed body (interceptors run before pipes).
- First request: `SET NX PX 60s` lock `{state:'processing'}` → handler → on 2xx store `{state:'completed', status, body}` for 24h (Lua compare-and-swap on the lock).
- Same key + same fingerprint while running → 409 `idempotency.error.in-progress`; after success → replay stored status + body with header `idempotent-replayed: true` (handler not called). Different fingerprint → 422 `idempotency.error.key-reused`.
- **Errors are not cached:** any thrown error (4xx `DomainError` included) or non-2xx status releases the lock, so the client can retry the same key.
- **Lock TTL is 60s, not renewed.** A handler running longer loses the lock; a concurrent retry may then execute again, and the late completion is logged (`idempotency lock expired…`) without overwriting. Same if writing the completed record fails (response still returned, logged). So money-moving writes (checkout, payments) **must also** have a DB unique constraint on the key (e.g. `Order.idempotencyKey`) — Redis alone is not the guarantee.
- An unreadable record (corrupt / older format) answers 422 key-reused rather than re-executing.
- Replay restores status + body only (no handler-set headers); handlers must return JSON-serializable values.

## Rate limit

`@fastify/rate-limit` registered by `registerRateLimit(app)` (`src/common/rate-limit.ts`, called in `main.ts` before `listen`), Redis store (keys `rl:*`), per client IP.

- **Client IP:** `clientIp()` takes the address `TRUSTED_PROXY_HOPS` (default 0 = socket peer; `fly.toml` sets 1 for the Fly edge) entries into `request.ips` (socket peer first, then X-Forwarded-For from nearest). Entries further left are client-supplied and ignored, so spoofing XFF cannot reset a bucket. Do **not** key on `request.ip`: `trustProxy: true` makes it the leftmost, spoofable XFF entry. Default `0` so a run without a proxy (local, direct internal address) never trusts a client-supplied XFF; only set it to the exact number of proxies that always sit in front of the API. The orders controller stores the same `clientIp()` on `Payment.clientIp` at checkout and payment retry — the worker passes it to VNPay as `vnp_IpAddr`.
- **Buckets:** every route shares one bucket of `RATE_LIMIT_MAX` (default 100) per `RATE_LIMIT_WINDOW` (default `1m`). Sensitive handlers add `@RateLimit('strict')` (method-level; wraps Fastify `RouteConfig`): `RATE_LIMIT_STRICT_MAX` (default 20) in a bucket per method + route — currently all OAuth start/callback routes, `/auth/refresh`, `/auth/logout`, `POST /orders/checkout`, `POST /orders/:id/payments`, `POST /platform/sub-orders/:id/refund`, `POST /platform/refunds/:id/retry`; future payment routes must add it. `@SkipRateLimit()` exempts a handler (`/health`, `/health/ready`, and the payment webhooks — see "Payments").
- Over the limit → 429 `common.error.rate-limited` + `retry-after` (the hook throws a `DomainError`, which Nest's Fastify error handler routes through `DomainErrorFilter`).
- **Redis down:** the default bucket fails open (availability); strict routes fail closed (500) — they must not lose brute-force protection.
- **Known limit:** a server-side caller (storefront SSR on Workers) shares its egress IP's bucket across all its users. When SSR starts calling the API, give it an allow-list / trusted-client key instead of raising the global limit.

## Pagination

List endpoints take `PageQuerySchema` (`?cursor=<ulid>&limit=1..100`, default 20) and return `PageSchema(item)` = `{ items, nextCursor }` — both in `@repo/core`. `src/common/pagination.ts`: `cursorPageArgs(query, 'desc' | 'asc')` → `{ take: limit + 1, where: { id: { lt | gt: cursor } }, orderBy: { id } }` (spread `where` into your filter), then `toPage(rows, query)` trims the look-ahead row and sets `nextCursor` (null on the last page). Relies on ULID ids sorting by creation time.

## Catalog (public, no auth)

All routes are unauthenticated, take `?locale=vi|en` (default vi; a missing en translation falls back to vi) and only expose `ACTIVE` products of `ACTIVE` vendors — anything else is 404 (detail) or absent (lists/search). Schemas: `@repo/core/schemas/catalog`.

| Endpoint                           | Notes                                                                                                                                                                 |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ---------- | -------------------------- |
| `GET /v1/categories`               | Whole tree (`children` nested), siblings by `sortOrder`                                                                                                               |
| `GET /v1/categories/:slug`         | Category + `breadcrumb` (root→self) + direct `children`; slug of either locale; unknown → 404 `common.error.not-found`                                                |
| `GET /v1/products`                 | `categorySlug` (includes subcategories), `vendorSlug`, `currency`, `minPrice`/`maxPrice` (minor units), `sort=newest                                                  | price_asc | price_desc | rating`, cursor pagination |
| `GET /v1/products/:slug`           | Variants with `stockAvailable` (= onHand − reserved; raw counters never exposed), images, vendor card, rating summary; unknown/hidden → 404 `product.error.not-found` |
| `GET /v1/search?q=`                | See search below; same page shape as the list                                                                                                                         |
| `GET /v1/vendors/:slug`            | Shop header + one page of its products (same query as the list minus `vendorSlug`); not ACTIVE → 404 `vendor.error.not-found`                                         |
| `GET /v1/platform-settings/public` | `defaultCurrency`, `supportedCurrencies`, `maxCouponStack`                                                                                                            |

- **Pagination:** the cursor is always the last item's product id. Every sort (newest = constant key, so `id DESC`) is a keyset on `(sort_key, id DESC)` where the key is derived in SQL from the cursor product (`ProductsRepository.listVisibleIds`). The cursor product's key is read without the visibility filter, so paging survives it being hidden. Price filters/sorts without `currency` use `PlatformSettings.defaultCurrency`. Known perf limit (no migrations this wave): each page scans all visible products; add indexes / a newest fast path later. `rating` sorts by average (2 dp), unrated last.
- **Search** (`ProductsRepository.searchVisibleIds`, raw SQL via `$queryRaw` bound parameters): a product matches when any translation satisfies `search_vector @@ websearch_to_tsquery('simple', q)` (accent-sensitive; `simple` config, no stemming), OR `q <% name` (pg_trgm word similarity, typo tolerant), OR the accent-folded query is a substring of the ASCII slug (this gives unaccented Vietnamese matching; there is no `unaccent` extension and no migrations were added). Rank = ts_rank + word_similarity (+0.5 slug hit), keyset-paginated. Limits: unaccented queries only match slug text (keep slugs transliterated from the name); word order must match for the slug path.
- Rating summary comes from `reviews` (`average` null when none), computed by `computeRatingSummary(prisma, productId)` in `src/common/rating-summary.ts` (shared by product detail and the reviews list).

## Auth (Golden Rule #5)

| Endpoint                                      | Guard                        | Behaviour                                                                                                                                                                       |
| --------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/auth/google?app=web\|admin`          | `OAuthStartGuard`            | Sets `oauth_state` cookie (random state + app), 302 → Google                                                                                                                    |
| `GET /v1/auth/google/callback`                | `OAuthCallbackGuard`         | Checks `?state` == cookie (login-CSRF), resolves user, sets refresh cookie, 302 → `AUTH_REDIRECT_URL_WEB\|ADMIN`. Any failure → 302 there with `?error=auth.error.oauth-failed` |
| `GET /v1/auth/facebook`, `/facebook/callback` | same                         | same                                                                                                                                                                            |
| `POST /v1/auth/refresh`                       | cookie                       | Rotates the refresh cookie, returns `{ accessToken, tokenType: 'Bearer', expiresIn }`                                                                                           |
| `POST /v1/auth/logout`                        | cookie                       | Revokes the session (token family), clears cookie, 204 (idempotent)                                                                                                             |
| `GET /v1/auth/me`                             | `JwtAuthGuard`, `RolesGuard` | Current user profile + effective roles + vendorId                                                                                                                               |

- **Frontend flow:** navigate to `/v1/auth/<provider>?app=…` → land on the app's `/auth/callback` → `POST /v1/auth/refresh` (`credentials: 'include'`) → keep the access token in memory; call refresh again on 401 `auth.error.token-expired`.
- **User resolution** (`AuthService.resolveOAuthUser`, one `$transaction`): known identity → login; provider-**verified** email matching a `User` → link new `OAuthIdentity`; else create `User` + `OAuthIdentity` + `UserRole CUSTOMER` (ULIDs). Unverified emails are never linked and never stored on `User.email` (blocks pre-account-takeover). Facebook emails are always treated as unverified (Graph API gives no guarantee) — so a Facebook-only user has `User.email = null` and a later Google login with the same address creates a separate account (accepted trade-off for takeover safety; an explicit "link account" flow is future work). Emails are stored and matched lowercase — keep every writer (seed included) lowercasing.
- **Access JWT** (HS256, `JWT_ACCESS_SECRET`, `JWT_ACCESS_TTL` = 15m): `{ sub, roles, vendorId? }` from `UserRole` rows; vendor roles count only while the vendor is `ACTIVE`; `vendorId` = oldest active vendor role. Roles are re-read on every refresh.
- **Refresh JWT** (HS256, `JWT_REFRESH_SECRET`, `JWT_REFRESH_TTL` = 30d): `{ sub, fid, jti }` in cookie `refresh_token` (HttpOnly, Secure, SameSite=Lax, Path=`/v1/auth`). State in Redis, no DB table: `auth:rt:family:<fid>` = `{ userId, current, prev, rotatedAt }` (sha256 hashes), TTL slides on rotation. Rotation is an atomic Lua compare-and-swap. Presenting `prev` within `REFRESH_REUSE_GRACE_MS` (10s) is a benign concurrent refresh (two tabs, SSR + client, StrictMode): it gets an access token but no new cookie, and the family survives (logged at info; the window uses the Redis server clock). Any other non-current token deletes the family (reuse detection → that session is logged out). The DB lookup for the access token runs _before_ the swap, so a DB failure never strands the client with a rotated-away cookie. Limit: if a successful refresh response is _lost in transit_ and the client retries within 10s, it keeps the stale cookie and is logged out at its next refresh — frontends should single-flight refresh calls (one in-flight refresh shared by all callers).
- **Protecting routes:** import `AuthModule`, then `@UseGuards(JwtAuthGuard, RolesGuard) @Roles('VENDOR_OWNER')`; read the caller with `@CurrentUser() user: AuthUser` (`{ id, roles, vendorId? }`). `RolesGuard` fails closed — a guarded route without `@Roles` is 403; use `@Roles(...ALL_ROLES)` for "any signed-in user".
- **Known limits:** access tokens stay valid until expiry (≤ 15m) after logout, family revocation, vendor suspension or role removal (no denylist / per-user session index yet) — services must re-check vendor status/ownership in the DB before destructive vendor or payout actions rather than trusting `req.user.vendorId` alone. The refresh cookie is always `Secure` (Golden Rule #5): Chrome/Firefox accept it on `http://localhost`, Safari may not — use Chrome for local login. SameSite=Lax means the API must be same-site with the web/admin origins in prod (e.g. `api.example.com` + `example.com`), otherwise the refresh cookie isn't sent. `TokenResponse` / `MeResponse` live in `@repo/core/schemas/me`; `src/auth/auth.schemas.ts` keeps only the server-internal schemas (token claims, `AuthUser`, OAuth profile).

## Cart (`src/cart/`)

All routes `@Roles('CUSTOMER')`, scoped to `req.user.id`; shapes in `@repo/core/schemas/cart`. Prices are never stored — every read joins the current variant price. `?locale=vi|en` (default vi) picks the product name/slug (falls back to any translation).

| Endpoint                                   | Behaviour                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/cart`                             | Lines grouped by vendor (oldest line first): `unitPrice`, `lineTotal`, `stockAvailable`, `unavailable` (product not ACTIVE or vendor not ACTIVE). Per-group `subtotals` are per currency over available lines; `hasMixedCurrency` flags a mixed cart. Does not create a Cart row.                                                                                                                     |
| `PUT /v1/cart/items/:variantId {quantity}` | `@Idempotent`. Sets the quantity; `0` removes (also works for unavailable lines). Unknown variant → 404 `product.error.variant-not-found`; product/vendor not ACTIVE → 409 `product.error.not-available`; over stock → 409 `cart.error.quantity-exceeds-stock`.                                                                                                                                       |
| `DELETE /v1/cart/items/:variantId`         | `@Idempotent`. Removes the line; absent line is a no-op. Returns the cart.                                                                                                                                                                                                                                                                                                                            |
| `POST /v1/cart/merge {items[]}`            | `@Idempotent`. Guest-cart merge: quantities add to existing lines (duplicates summed), clamped to `stockAvailable`; a merge never lowers an existing line; unknown/unsellable variants are dropped. Returns `{ cart, adjustments[] }` (`CLAMPED` / `UNAVAILABLE`). Same key replays; a **new key adds the quantities again**, so the client calls merge once after login, then clears the guest cart. |
| `GET /v1/cart/shipping-options`            | Active `ShippingMethod`s per vendor present in the cart (sellable lines only), `{ groups: [{ vendorId, methods }] }`.                                                                                                                                                                                                                                                                                 |

`POST /v1/orders/:orderId/sub-orders/:id/confirm-received` (customer confirms receipt) is documented under "Fulfilment + wallet" below.

**Checkout transaction** (`CheckoutService`, one interactive `$transaction`, READ COMMITTED + row locks, 15s timeout; any error rolls back everything):

1. `PlatformSettings` (missing → 500) and the buyer (`primaryLocale`).
2. Variants + product + vendor + categories. Unknown → 404 `product.error.variant-not-found`; product or vendor not ACTIVE → 409 `product.error.not-available`.
3. One currency for every line, and in `supportedCurrencies` (D6) → else 422 `checkout.error.currency-mismatch`. The provider must charge that currency (`providerSupportsCurrency`: VNPay VND only, Stripe VND/USD) → else 422 `payment.error.provider-currency-unsupported`.
4. Address must be the buyer's (404 `checkout.error.address-not-found`) → `ShippingAddressSnapshot` JSON on each sub-order.
5. Group by vendor (first-appearance order). Every vendor of the order must have a `Wallet` in the order currency (one currency per vendor, see "Vendor catalog") → else 422 `checkout.error.currency-mismatch {vendorId, currency}` (defence in depth: the catalog already refuses other currencies; a sub-order the wallet cannot hold would never be paid out). `shippingMethodIds` must give exactly one active method per vendor of the order, owned by it and in the order currency: unknown / inactive / foreign / second-for-a-vendor → 422 `checkout.error.shipping-method-invalid {shippingMethodId}`; vendor without one → 422 `…-missing {vendorId}`.
6. Coupons: `SELECT … FOR UPDATE` (id order) on the coupon rows matching the codes (platform: `vendor_id IS NULL`; vendor: `vendor_id` among the order's vendors), then count redemptions (total + this user). Codes are case-insensitive: `CouponCodeSchema` trims + uppercases the request, and the lookup compares `upper(code)` (so a coupon stored in any case matches; seeds are uppercase). A code resolves to the **active platform coupon** with that code if there is one (platform codes win, vendors cannot shadow them), otherwise to every vendor coupon with that code of the vendors in the order; nothing → 404 `coupon.error.not-found {code}`. A coupon in another currency → 422 `checkout.error.currency-mismatch {code}`. Eligibility/limits/stacking are `priceOrder`'s (`coupon.error.*`); when a code matches several vendors' coupons, any ineligible one rejects the whole checkout.
7. Commission bps per line via `resolveCommissionBps` (vendor override → lowest category override → platform), then `priceOrder` (D5-D8).
8. Reserve stock (D4) line by line **in variant-id order** (deadlock-free between concurrent checkouts): `UPDATE … SET stock_reserved = stock_reserved + qty WHERE id = ? AND stock_on_hand - stock_reserved >= qty`; 0 rows → 409 `checkout.error.out-of-stock {variantId}` (earlier reservations roll back too).
9. Insert `Order` (`idempotencyKey` = header key, `paymentDeadlineAt` = now + `paymentTimeoutMinutes`, `zaloOptIn` from the body), `SubOrder`s (`discountAmount` = vendor discount, `platformDiscountAmount`, `commissionAmount` from the pricing result), `OrderItem`s (title in the buyer's `primaryLocale`, fallback vi; attributes; unit price; line total), `CouponRedemption`s (all carry `orderId`; vendor ones also `subOrderId`), `Payment {PENDING, attemptNo 1, provider, amount = grandTotal, clientIp}`, outbox `order.created` + `payment.requested`; Zalo `ORDER_PLACED` messages (`queueZaloMessages`, see "Zalo notifications"); delete the purchased variants' lines from the server cart (whole line, even if the cart held more than was bought — the body, not the cart, drives checkout). **No ledger rows** (D3: escrow IN is written by the payment confirmation, T3.1).

- **Idempotency backstop:** before the transaction, and again after **any** failure of it (a concurrent same-key winner shows up as P2002 on `orders.idempotency_key`, or as out-of-stock on the unit it just reserved), the order with that key is looked up: same user + same items/shipping methods/provider → that order is returned (201); another user or a different body → 422 `idempotency.error.key-reused` (address and coupon codes are not compared). The after-failure lookup never masks the real error: if it throws (incl. a key-reused verdict) or finds no winner, the ORIGINAL error is rethrown. Known limit: the key is unique globally, not per user (fixing it needs a migration to `(customer_id, idempotency_key)`); random ULID keys make collisions impractical.
- **Grand total 0** (free shipping + 100% coupons) is allowed and still creates a PENDING payment of 0 + `payment.requested`: the worker does not open a provider session for 0 and confirms it instead (implemented in T3.2, mirroring `PaymentConfirmationService.confirmZeroAmount`, see "Payments").
- **Outbox** (`aggregateType = 'order'`, `aggregateId = orderId`; payload schemas in `@repo/core/schemas/outbox`, ids only): `order.created {orderId, customerId}`, `payment.requested {orderId, paymentId, provider, attemptNo}`, `order.cancelled {orderId, customerId, reason: 'CUSTOMER' | 'PAYMENT_EXPIRED'}`; fulfilment adds `sub-order.shipped` / `sub-order.delivered {orderId, subOrderId, customerId}` and `sub-order.completed {orderId, subOrderId, vendorId}`.

**Cancellation contract** — `cancelOrder(tx, orderId, reason)` in `order-cancellation.ts`, shared with the payment-expiry job (implemented: `workers/jobs` `expire-unpaid-orders` mirrors it; returns `'cancelled' | 'not-found' | 'not-cancellable'` without writing in the last two cases): lock the order row (`SELECT … FOR UPDATE` — the payment confirmation must take the same lock first); require every sub-order AWAITING_PAYMENT; sub-orders → CANCELLED + `cancelledAt` with `WHERE status = 'AWAITING_PAYMENT'` (count mismatch throws → rollback); release `stock_reserved` per variant in id order, clamped at 0; delete the order's CouponRedemptions; PENDING payments → FAILED; `orders.status` = `deriveOrderStatus(...)`; outbox `order.cancelled`; Zalo `ORDER_CANCELLED` messages (`queueZaloStatusMessages`). Ownership is checked by the caller; it does not look at `paymentDeadlineAt` — the expiry job selects overdue orders itself and passes `PAYMENT_EXPIRED`. The clamp at 0 is only a safety net (the status guard prevents a double release).

**Contracts for later tasks:** the T2.2 worker writes `Payment.redirectUrl` / `expiresAt` only `WHERE status = 'PENDING'` (a retry or cancel may have failed the attempt meanwhile). Payment confirmation (T3.1, done) locks the order row first; a CONFIRMED result for a FAILED attempt of a still-unpaid order pays the order, for a cancelled order it goes to the refund path — see "Payments".

Tests: `test/integration/orders.spec.ts` (single + two-vendor money, out-of-stock rollback, concurrent last unit, idempotency replay + DB backstop, coupon limit, shipping validation, client prices ignored, cancel, 404 for others, payment session 202/200, retry rules).

## Payments: webhooks + confirmation (`src/payments/`, T3.1)

`PaymentsModule`: `PaymentWebhooksController` (thin) → `PaymentWebhooksService` (verify with `@repo/payments`, map outcomes) → `PaymentConfirmationService` (the transaction). Exports `PaymentConfirmationService` and `PAYMENT_PROVIDERS`.

| Endpoint                           | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/payments/webhook/stripe` | Raw body (see below) → `verifyWebhook`. Bad/missing signature or stale timestamp → 400 `payment.error.signature-invalid`, nothing read or written. IGNORED event types → 200. Every handled outcome (incl. unknown payment, amount mismatch, and an authentic event whose amount/currency the adapter cannot read — null total, unknown currency) → 200 `{ received: true }` (a retry would not change it; logged). Unexpected/DB error → 500 so Stripe retries.                                         |
| `GET /v1/payments/webhook/vnpay`   | IPN. Always HTTP 200 + `VNPAY_IPN_RESPONSE` JSON, checks in VNPay's order: signature (incl. foreign `vnp_TmnCode`) `97` → payment exists (for provider VNPAY) `01` → amount/currency `04` → already processed `02` → applied `00` (confirmed, failed recorded, refund requested, manual review). Unexpected error `99`. (Deviation: an authentic IPN whose `vnp_Amount` is unparseable answers `04` before the payment lookup — the adapter rejects it while verifying.) `00`/`02` stop VNPay's retries. |
| `GET /v1/payments/return/vnpay`    | Browser return (`VNPAY_RETURN_URL`). Verifies the signature, reads the payment's order + customer `primaryLocale`, then 302: signed success → `{WEB_ORIGIN}/{locale}/order/success?orderId=…`; signed failure → `/{locale}/order/payment-failed?orderId=…`; bad signature / unknown payment / VNPay not configured → `/vi/order/payment-failed?error=<errorCode>`. **Never changes state** (only the IPN does): the success page must poll the order until it is PAID.                                   |

- **Public routes:** no JWT (authenticity = provider signature), not `@Idempotent()` (providers send no `Idempotency-Key`; replays are absorbed by the transaction below), excluded from OpenAPI/SDK (`@ApiExcludeController`, no frontend calls them). **Rate limit:** both webhooks skip it — providers deliver from shared egress IPs and retry on errors, so an IP bucket would drop real notifications; the signature check runs before any DB I/O, so a flood costs one HMAC per request. The return route keeps the default bucket (browser traffic).
- **Raw body:** `@SignedWebhookRoute()` (`src/common/raw-body.ts`) = `RouteConfig({ rateLimit: false, rawBody: true })` (one decorator: Nest's `@RouteConfig` metadata does not merge, so it cannot be stacked with `@SkipRateLimit()`). `registerRawBodyCapture(app)` (in `main.ts` + test harness, before `init`) adds a `preParsing` hook that, only for routes with `rawBody: true`, buffers the body (≤ body limit), stores it on `request.rawBody` and replays the same bytes to the normal JSON parser. All other routes parse exactly as before and keep no raw copy.
- **Provider config** (`payment-providers.ts`, `PAYMENT_PROVIDERS` = `Partial<Record<provider, PaymentProvider>>` built from env at boot, no network I/O): VNPay enabled when `VNPAY_TMN_CODE` + `VNPAY_HASH_SECRET` are set (`VNPAY_PAY_URL` / `VNPAY_API_URL` default to sandbox), Stripe when `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET` are set. A missing provider logs a warning at boot and its webhook answers 503 `payment.error.provider-unavailable` (boot never fails on it). `VNPAY_RETURN_URL` is read by the worker (session creation), not by the API.
- **PII:** payloads are never logged. `Payment.rawPayload` stores a Zod-whitelisted extract only (`minimalRawPayload`): VNPay `vnp_TxnRef/Amount/ResponseCode/TransactionStatus/TransactionNo/BankCode/CardType/PayDate` (no `vnp_OrderInfo`); Stripe event `id/type/created` + session `id/payment_status/amount_total/currency` (no `customer_details`).

**Confirmation transaction** (`PaymentConfirmationService.apply`, one interactive `$transaction`, 15s timeout): look up the payment (must match the webhook's provider, else `not-found`) → `SELECT … FROM orders WHERE id = $1 FOR UPDATE` (same first lock as `cancelOrder` / payment retry) → `SELECT … FROM payments … FOR UPDATE` → re-read both.

1. **Amount/currency ≠ `Payment.amount`/`currency`** → a PENDING payment becomes FAILED (a CONFIRMED result also stores its `providerTxnId` + minimal `rawPayload` on the row, so money the provider holds can be traced and refunded manually), error logged (ids + amounts) → `amount-mismatch` (VNPay `04`). Checked before "already processed", as VNPay specifies.
2. **FAILED result** → PENDING payment → FAILED (`failed`; order stays AWAITING_PAYMENT, the customer can retry); any other status → `already-processed` (`02`).
3. **CONFIRMED result, payment CONFIRMED/REFUNDED** → `already-processed` (replay; nothing written).
4. Otherwise (PENDING, or FAILED = superseded / failed earlier) the money is real: payment → CONFIRMED + `providerTxnId` + minimal `rawPayload` (`updateMany WHERE status IN (PENDING, FAILED)`), then by order status:
   - **AWAITING_PAYMENT → `confirmed`:** other PENDING attempts of the order → FAILED; sub-orders AWAITING_PAYMENT → PAID (`updateMany WHERE status`, count must match); stock per variant **in variant-id order** `stock_on_hand -= qty, stock_reserved -= qty WHERE stock_on_hand >= qty AND stock_reserved >= qty` — if that guard fails (counter edited below the reservation; should not happen) the error is logged, both counters are clamped at 0 and the payment is still confirmed; ledger per sub-order with `paid_i > 0` (`subOrderPaid` = subtotal + shipping − discountAmount − platformDiscountAmount; `computeEscrowInPostings`: `CUSTOMER −paid_i`, `PLATFORM_ESCROW +paid_i`, entry type `ESCROW_IN`, one `txnGroupId` per sub-order, `orderId` + `subOrderId` set, `vendorId` null, `assertZeroSum` before `createMany`); `orders.status` = `deriveOrderStatus` (PAID); outbox `order.paid {orderId, customerId}`.
   - **CANCELLED → `refund-requested`** (paid after the customer cancelled / the deadline expired; stock + coupons were already released and nothing was escrowed): per sub-order with `paid_i > 0`: escrow IN group (`ESCROW_IN`), a `Refund` PENDING of `paid_i` (`paymentId` = this payment, `requestedById` = the customer, `reason` = `payment-after-cancellation`), the refund postings in their own group (`computeRefundPostings`: `PLATFORM_ESCROW −paid_i`, `CUSTOMER +paid_i`, `REFUND` — same as the admin refund, T3.5), outbox `refund.requested {refundId, orderId, subOrderId}`. Sub-orders and order stay CANCELLED; escrow nets to 0. The Refund insert is `INSERT … ON CONFLICT (sub_order_id) WHERE status <> 'FAILED' DO NOTHING` (the partial unique index; a P2002 cannot be caught inside a Postgres transaction without a savepoint): a conflict means a refund was written concurrently without the order lock → throw → rollback → the provider retries and lands in the next case. The worker's `refund.requested` handler (T3.2) calls the provider; with several sub-orders that is several partial refunds of one payment.
   - **Any other order status, an AWAITING_PAYMENT order with a sub-order not AWAITING_PAYMENT (inconsistent — never thrown, so the provider is not looped on a rollback), a CANCELLED order whose sub-orders already carry an active refund (a second late payment), or Σ `paid_i` ≠ payment → `manual-review`:** a duplicate payment (e.g. the customer paid an old attempt and the retry). Payment CONFIRMED + one order-level escrow IN group (`subOrderId` null) and an **error log** "held in escrow, refund it manually". No `Refund` row: the table allows one active refund per sub-order and the payout job skips sub-orders with a PENDING/SUCCEEDED refund, so a row here would block the real sale's payout / admin refund. Automating this needs a migration (order-level refunds).

**Manual review — how ops reconcile it (no endpoint yet).** The duplicate payment's money sits in escrow under an order-level `ESCROW_IN` group (`CUSTOMER −x`, `PLATFORM_ESCROW +x`, `subOrderId` null). Payouts and refunds only move per-sub-order `paid_i`, so after every sub-order is paid out / refunded that order's `PLATFORM_ESCROW` balance stays at **+x** instead of 0, and the customer is owed x. Until a ledger-adjustment endpoint exists:

1. **Find** them: the error log "held in escrow, refund it manually" (ids + amounts), or orders with more than one CONFIRMED payment / an `ESCROW_IN` row with `sub_order_id IS NULL`.
2. **Refund the duplicate at the provider** (VNPay merchant portal / Stripe dashboard) using that payment's `providerTxnId`. Never refund the sale payment: the admin refund endpoint targets the first-confirmed payment equal to the order total (see "Refunds"), so a duplicate does not receive a platform refund (unless no payment equals the total — then the fallback, with its `warn` log, needs a manual check).
3. **Record it** in the ops reconciliation log (orderId, paymentId, provider refund reference, date) and, with a ticket reference, set that duplicate `Payment.status` to REFUNDED by hand. Do **not** hand-write ledger rows: the order's escrow stays at +x as a known, logged exception (finance reports must subtract these entries).
4. **Future work:** an admin ledger-adjustment / order-level refund endpoint (`PLATFORM_ESCROW −x`, `CUSTOMER +x`, own `txnGroupId`, audited, with a provider refund through the worker) — needs a migration for order-level refunds.

- **Deviation from the T2.1 contract:** a CONFIRMED result for an attempt already FAILED by a retry, while the order is still AWAITING_PAYMENT, **pays the order** (and fails the newer PENDING attempt) instead of refunding: the customer paid the exact grand total, and a Refund on sub-orders that the newer attempt may still pay would block their payout. If the newer attempt is paid too, it becomes `manual-review`.
- **Concurrency:** webhook vs cancel vs retry serialise on the order row lock; whichever commits first wins and the other sees the result (cancel after confirm → 409; confirm after cancel → refund path).
- **Zero amount:** `PaymentConfirmationService.confirmZeroAmount(paymentId)` (exported) confirms a payment of 0 through the same `apply` path (`providerTxnId` = paymentId, `rawPayload {zeroAmount: true}`, provider unchanged — the enum has no "none"); no ledger rows (`paid_i = 0` groups are skipped); non-zero → `payment.error.amount-mismatch`; on an order that is no longer AWAITING_PAYMENT (e.g. cancelled) it writes nothing and returns `already-processed`. Nothing calls it in the API: the worker does the equivalent in its `payment.requested` handler when `Payment.amount = 0` (implemented, T3.2: `workers/jobs/src/domain/zero-amount.ts` mirrors `markOrderPaid` with the same lock order).
- **Outbox:** `order.paid {orderId, customerId}`, `refund.requested {refundId, orderId, subOrderId}` (`@repo/core/schemas/outbox`, aggregate = order).

Tests: `test/integration/payments.spec.ts` (VNPay IPN confirm with two vendors + vendor and platform coupons: payment / sub-orders / order, stock, ledger zero-sum per group and = pricing, outbox; replay → `02` + one ledger set; bad signature / tampered amount / foreign terminal → `97`, no writes; check order `01` → `04` → `02`; FAILED result; payment after cancel → refunds + ledger + outbox, replay-safe; superseded attempt pays the order, second payment → manual review; concurrent IPN + cancel consistent; Stripe confirm via raw body, PII stripped, replay; Stripe bad signature and re-serialised body → 400; ignored / expired / currency mismatch; return route redirects without state change; zero amount; providers not configured → 503).

## Vendor catalog (`src/vendor/`)

All routes `@Roles('VENDOR_OWNER','VENDOR_STAFF')`; the vendor comes ONLY from `req.user.vendorId` (no vendorId in the JWT -> 403 `vendor.error.not-active`). Every query is scoped by it, so another vendor's product / variant / shipping method is 404. Every write runs in a `$transaction` that first re-reads `vendors.status` (`SELECT ... FOR SHARE`, `assertVendorActive`): SUSPENDED -> 403 `vendor.error.suspended`, other non-ACTIVE -> 403 `vendor.error.not-active` (a stale JWT cannot bypass it). Reads stay open. `VendorMembershipGuard` re-checks in the DB that the caller still holds a vendor role on `vendorId` (a revoked staff member loses access immediately, not after the 15m JWT). PUT on a BLOCKED product is refused (409 `product.error.blocked`). Mutations carry `@Idempotent()`. Shapes: `@repo/core/schemas/product-admin` (`VendorProduct`, `VendorProductPage`, `VendorProductVariant`, `ProductUpsert`, `VariantStockUpdate`) + `shipping-method`.

| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/vendor/products?status&cursor&limit`                              | Own products newest first (`VendorProductPage`; `name` = vi name, `stockOnHand` = sum)                                                                                                                                                                            |
| `POST /v1/vendor/products`                                                 | `ProductUpsert` -> 201 DRAFT `VendorProduct`; variant/image `id` not allowed                                                                                                                                                                                      |

- **Slugs / skus:** `(locale, slug)` and `sku` are globally unique -> 409 `common.error.conflict {field}` (pre-checked in the transaction; a lost race on the unique index is mapped to the same 409). Both translations (vi + en) are required by `ProductUpsertSchema`.
- **Variants** are matched by `id`, else by `sku` within the product. A variant missing from the payload is deleted only if no `OrderItem` and no `CartItem` references it, otherwise 409 `product.error.variant-in-use` (the vendor sets stock to 0 instead; there is no per-variant archive).
- **Stock:** never a blind overwrite. PUT and PATCH use `UPDATE ... WHERE stock_reserved <= :new` (`updateMany`), the same row-lock semantics as checkout's reservation `UPDATE`, so a concurrent reservation cannot be undercut; 0 rows -> 409 `product.error.stock-below-reserved {stockReserved}` (and the whole PUT rolls back).
- **One currency per vendor = its wallet currency.** A vendor has exactly one `Wallet`, created in `PlatformSettings.defaultCurrency` at approval, and payouts credit only that wallet (`release-payouts` skips a sub-order in any other currency, forever). So product create / PUT and shipping-method create / PUT require the price currency = `Wallet.balanceCurrency` (`assertWalletCurrency`, `vendor-scope.ts`, in the write transaction) → else 422 `common.error.validation-failed {field: 'currency', currency, expected}`; checkout re-checks it (step 5 above). Changing `defaultCurrency` later does not move existing vendors (their wallet keeps its currency); multi-currency vendors would need one wallet per currency (a migration).
- **Prices:** minor units; currency must be in `PlatformSettings.supportedCurrencies` (else 422 `common.error.validation-failed`) and = the wallet currency (above), all variants share the product currency. **`Product.basePriceAmount` is always `MIN(variant priceAmount)`** (currency = product currency), recomputed in the same transaction on create / PUT, because the public catalog filters/sorts on it while cart/checkout charge the variant price; the client-sent `basePrice.amount` is ignored (only its currency is used). Variant prices change only through PUT.
- **Images:** array order = display order (`sortOrder` = index); `{ key }` is checked with `StorageService.assertOwnedKey(key, { type: 'vendor', vendorId })` and stored as `publicUrl(key)` in `ProductImage.url` (what public catalog reads return); `{ id }` keeps an own image (foreign id -> 404 `common.error.not-found`); images not listed are deleted (DB rows only, objects stay in S3). `Product.primaryImageUrl` = the first image (lowest `sortOrder`) or null.
- **Search:** `product_translations.search_vector` is a _generated_ column (no trigger, nothing to maintain in the app); a published product is searchable immediately and a rename is picked up on PUT.

| --------------------------------------- | ---------- | -------------------------------------- |
| AWAITING_PAYMENT                        | PAID       | SYSTEM (payment confirmation, T3.1)    |

## Storage / uploads (roadmap D13)

`StorageModule` (`src/storage/`) exports `StorageService`; import it in a feature module to validate or read keys. AWS SDK v3 (`@aws-sdk/client-s3` + `s3-request-presigner`), `forcePathStyle` locally. Local S3 = RustFS (compose service `s3`, ports 9000/9001, creds `rustfsadmin`; Docker Hub `minio/minio` is no longer pullable) plus the one-shot `s3-init` job (`docker/s3-init.sh`) that creates `kyc` (private) and `media` (public read).

- **Env** (`env.ts`): `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` (required), `S3_FORCE_PATH_STYLE` (default true; set false for R2 virtual-host style if desired), `S3_BUCKET_KYC` (`kyc`), `S3_BUCKET_MEDIA` (`media`), `MEDIA_PUBLIC_BASE_URL` (default `http://localhost:9000/media`; `publicUrl` = base + `/` + key, so locally the path reads `/media/media/vendors/…` — the key itself starts with `media/`).
- **`POST /v1/uploads/presign`** (`UploadsController`, `JwtAuthGuard` + `RolesGuard`, body `PresignRequest`, returns `PresignResponse`): `kyc` needs `CUSTOMER` (key `kyc/{userId}/{ulid}.{ext}`, jpeg/png/webp/pdf); `product-image` / `vendor-logo` need `VENDOR_OWNER|VENDOR_STAFF` with `vendorId` from the token (key `media/vendors/{vendorId}/{ulid}.{ext}`, jpeg/png/webp). Max 10 MB, URL valid 5 min. Errors: `upload.error.content-type-not-allowed` (422), `upload.error.too-large` (413), `common.error.forbidden`. No `@Idempotent()`: presigning writes no state (a retry just returns another unused key). Default rate-limit bucket.
- **Content-Type and size are enforced by S3, not by us:** the PUT is signed with `content-type` and `content-length` as signed headers, so a PUT with a different type or byte length gets 403 (verified against RustFS). The client must send `headers` from the response and a body of exactly the declared `size`. We do not inspect the bytes (no magic-number sniffing / virus scan).
- **`StorageService`:** `presignPut(purpose, owner, contentType, size)`, `presignGet(key)` (kyc keys only, 60s TTL — authorise platform staff in the caller), `publicUrl(key)` (media keys only), `assertOwnedKey(key, owner)` → returns the key or throws `upload.error.invalid-key`. `owner` = `{ type: 'user', userId }` for kyc keys, `{ type: 'vendor', vendorId }` for media keys (always from `req.user`). It checks owner + shape only (media keys: images only), not the exact purpose and not that the object exists — HEAD it if that matters. Signed `content-length` is verified on RustFS only; smoke-test on R2 before prod. In production `S3_ENDPOINT` / `MEDIA_PUBLIC_BASE_URL` must not be localhost (env refine). **Any feature that persists a client-echoed key (vendor application, product images, logo) must call `assertOwnedKey` first.**
- The S3 client is lazy (no connection at construction), so `openapi:export` needs no S3 stub. Unit tests mock the presigner (`test/storage/`, `test/http/uploads.http.spec.ts`); there is no Testcontainers S3 test (the harness only starts Postgres + Redis).

## Refunds (`src/refunds/`, T3.5, roadmap D12)

Admin-initiated, always the **whole** sub-order (`paid_i`, D7; no partial refunds — D15). `PlatformRefundsController` (`/v1/platform/...`), shapes in `@repo/core/schemas/refund`, money math in `@repo/core` `refundAmount` / `refundPostings`.

| Endpoint                                           | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/platform/sub-orders/:id/refund {reason}` | `PLATFORM_ADMIN` only, `@Idempotent()` + `@RateLimit('strict')` → 201 `Refund`. Unknown sub-order → 404 `sub-order.error.not-found`; the admin is the order's customer → 403 `common.error.forbidden`; otherwise not refundable → 409 `refund.error.not-refundable {subOrderId, reason: 'status' \| 'payout-released' \| 'no-confirmed-payment' \| 'refund-exists'}`.                                           |
| `POST /v1/platform/refunds/:id/retry`              | `PLATFORM_ADMIN` only, `@Idempotent()` + `@RateLimit('strict')`, no body → 201 the new PENDING `Refund`. Recovery path for a provider refund that FAILED — see "Retry of a FAILED refund" below. Unknown refund → 404 `common.error.not-found`; own order → 403 `common.error.forbidden`; otherwise 409 `refund.error.not-refundable {subOrderId, reason: 'refund-not-failed' \| 'status' \| 'refund-exists'}`. |
| `GET /v1/platform/refunds?status=&cursor=&limit=`  | `PLATFORM_STAFF \| PLATFORM_ADMIN`; newest first, `RefundPage` of `RefundListItem` (= `Refund` + `orderId` + `vendorId`).                                                                                                                                                                                                                                                                                       |

**Refund transaction** (`RefundsService`, one `$transaction`, 15s timeout):

1. Lock the **order row first** (`SELECT … FROM orders JOIN sub_orders … FOR UPDATE OF o` — same first lock as cancel and payment confirmation), then the sub-order row (`FOR UPDATE`), so concurrent refunds and fulfilment transitions serialise.
2. Refundable iff status ∈ {PAID, PROCESSING, SHIPPED, DELIVERED} **and** `payoutReleasedAt IS NULL` **and** the order has a CONFIRMED payment **and** no PENDING/SUCCEEDED refund exists. The payment refunded against is the **first-confirmed CONFIRMED payment whose amount + currency = the order's `grandTotalAmount` / `currency`** (`salePayment`): a duplicate payment that went to manual review also stays CONFIRMED and must not be the one refunded. The first confirmation paid the order, every later one is a duplicate; confirmation time = `Payment.updatedAt` (a CONFIRMED row is written only by its confirmation — other payment updates target PENDING rows), not `attemptNo` (a late payment of an older attempt is the duplicate). No exact match → the latest CONFIRMED attempt + a `warn` log. Interim rule (no migration): a proper fix records which payment the order consumed. COMPLETED is not refundable (payout window).
3. Amount = `refundAmount` = `subtotal + shipping − discountAmount − platformDiscountAmount`; Σ non-FAILED refunds of the payment must stay ≤ `Payment.amount` (else 500, data corruption).
4. Insert `Refund {PENDING, paymentId = the CONFIRMED payment, requestedById = admin}`. P2002 on the partial unique index `refunds_sub_order_id_active_key` → 409 not-refundable (backstop; the order lock already prevents it).
5. Sub-order → REFUNDED (`updateMany … WHERE status = <current>`; count ≠ 1 → 409).
6. Stock: only when the sub-order was PAID / PROCESSING (goods still with the vendor), `stock_on_hand += qty` per variant in variant-id order. From SHIPPED on the goods may never come back, so stock is **not** returned (the vendor corrects it via `PATCH /vendor/variants/:id/stock` if they do).
7. Ledger, own `txnGroupId`, `entryType = REFUND`, `orderId` + `subOrderId` set, `vendorId` null (neither row is a vendor account): `PLATFORM_ESCROW −paid_i`, `CUSTOMER +paid_i`; `assertZeroSum`. Written now, not when the provider confirms — the escrow no longer owes this money to the vendor.
8. `orders.status` = `deriveOrderStatus(...)` (PARTIALLY_REFUNDED / REFUNDED).
9. Outbox `refund.requested {refundId, orderId, subOrderId}` (`aggregateType 'order'`).

**`paid_i = 0`** (free shipping + 100% coupons): the Refund is created **SUCCEEDED** directly, no ledger rows (nothing moved), no `refund.requested` (no provider call); status/stock/order status still change.

**Contract for the worker (`refund.requested` handler — implemented in T3.2, see `workers/jobs/CLAUDE.md` "Refund handler"):** skip unless the Refund is PENDING; call `provider.refund` for `Refund.amount` against the payment's `providerTxnId`; on success set SUCCEEDED + `providerRefundId` (`WHERE status = 'PENDING'`). On FAILED: keep the ledger and the sub-order REFUNDED (the customer is owed the money; the escrow already moved it to `CUSTOMER`), set the Refund FAILED, alert ops — the retry is `POST /v1/platform/refunds/:id/retry` (below), not another call of the sub-order refund endpoint (the sub-order is already REFUNDED). Do not mark `Payment` REFUNDED while another sub-order of the order is still refundable — this endpoint requires a CONFIRMED payment. The payout job must skip sub-orders that are REFUNDED or have a PENDING/SUCCEEDED refund. Every writer of `SubOrder.status` or `payoutReleasedAt` (T3.1 confirmation, T3.2 payout / auto-complete, T3.3 fulfilment) must lock `orders … FOR UPDATE` before the sub-order row (or update the sub-order with a `WHERE status = <from>` guard), so it serialises with refunds without a lock-order deadlock.

**Retry of a FAILED refund** (`RefundsService.retryRefund`, one `$transaction`, 15s timeout): lock the **order row first** (`orders JOIN sub_orders JOIN refunds … FOR UPDATE OF o`), then the refund row → the admin is the order's customer → 403 → retryable iff the refund is **FAILED** (else `refund-not-failed`) **and** its sub-order is REFUNDED (admin refund) or CANCELLED inside a CANCELLED order (late-payment refund, T3.1) (else `status`) **and** the sub-order has no PENDING/SUCCEEDED refund (else `refund-exists`) → Σ non-FAILED refunds of the payment + this amount ≤ `Payment.amount` (else 500) → insert a **new** PENDING `Refund` with the same `amount`, `currency`, `paymentId`, `subOrderId`, `requestedById` = the admin, `reason` = `retry of refund <failedId>` (a new id = a new provider idempotency id; the FAILED row stays as history) → outbox `refund.requested {refundId, orderId, subOrderId}`. **The ledger is never touched** (the original refund already moved `paid_i` from escrow to `CUSTOMER`); stock / sub-order / order status are unchanged. P2002 on `refunds_sub_order_id_active_key` → 409 `refund-exists` (backstop; the order lock serialises concurrent retries, so one wins and the other sees `refund-exists`). A dead-lettered (still PENDING) refund is not retryable here — requeue its outbox row (workers CLAUDE.md).

Tests: `test/integration/refunds.spec.ts` (1 of 2 → PARTIALLY_REFUNDED, both → REFUNDED, ledger zero-sum + escrow balance, stock only before SHIPPED, payout released / COMPLETED blocked, sequential + concurrent double refund, idempotent replay, AWAITING_PAYMENT / CANCELLED / no confirmed payment, 0 amount, STAFF 403 / self-refund 403 / unknown 404, list filter + cursor, refund picks the first-confirmed payment equal to the total over a duplicate CONFIRMED one, incl. a late payment of an older attempt; retry: after FAILED → new PENDING + outbox and ledger unchanged, late-payment refund of a CANCELLED order, PENDING / SUCCEEDED / already retried → 409, two concurrent retries → one, STAFF / own order 403, unknown 404).

- **Admin re-check:** settings PATCH and role grant/revoke re-read `PLATFORM_ADMIN` from the DB inside the transaction (`assertPlatformAdmin`, 403 otherwise), so a just-demoted admin's stale token cannot change them (nor re-grant itself); two admins demoting each other concurrently → one 200, one 403.

- **Templates (C7):** `CrmTemplateTextSchema` runs `assertCrmTemplate` inside the Zod pipe. `DomainErrorFilter` surfaces a custom Zod issue whose message is a 422 `ErrorCode` as that code + params (so links → 422 `crm.error.links-not-allowed {match}`, bad placeholder → `crm.error.unknown-placeholder {placeholder}`) instead of the generic `common.error.validation-failed`. - **Coupons (C10):** `assertCrmCoupon` — the caller vendor's own `VENDOR` coupon, `isActive`, `startsAt ≤ at < endsAt` (`at` = now for automations / drafts, the send time at schedule) and a code passing `assertCrmCouponCode`; anything else → 422 `crm.error.coupon-invalid {couponId}`.
- **Schedule** (one `$transaction`): owner + vendor ACTIVE → `pg_advisory_xact_lock` per vendor (two schedules cannot both pass the limit) → **row lock** `SELECT … FROM crm_campaigns … FOR UPDATE` and every check runs on the locked row (update / cancel take the same row lock, so a concurrent PUT either committed before and is validated, or waits and gets 409; the worker's SCHEDULED → SENDING move (`startCampaign`) locks it too) → must be DRAFT (409) → `{couponCode}` / coupon valid at send time → weekly limit → `hasEligibleAudience` (`LIMIT 1`) now (else 422 `crm.error.empty-audience`) → `updateMany WHERE status = 'DRAFT'` → SCHEDULED + `scheduledAt` → outbox `crm.campaign.scheduled {campaignId, vendorId}` (`aggregateType 'crm-campaign'`, **`nextAttemptAt` = send time**, so the dispatcher hands it to the worker when due; the worker re-checks `status = 'SCHEDULED'` and `scheduledAt ≤ now` under the row lock). `scheduledAt: null` = now; in the past or > 30 days ahead → 422 `common.error.validation-failed {field: 'scheduledAt'}`. The audience is resolved again at send time (worker, `workers/jobs/CLAUDE.md` "CRM"). Transaction bounded with `{ maxWait: 5s, timeout: 15s }`.
- **Weekly limit (C10):** campaigns SCHEDULED / SENDING / SENT of the vendor are points at their `scheduledAt`; scheduling at `t` is refused (429 `crm.error.campaign-limit-reached {limit}`) when some sliding 7-day window `[s, s + 7d)` would hold more than `PlatformSettings.crmMaxCampaignsPerWeek` (checked exactly: `crmMaxCampaignsPerWeek + 1` points less than 7 days apart). CANCELLED ones free their slot.
- **Statistics (C1–C3) — `CrmCustomersRepository`, raw SQL:** "valid" sub-orders = `PAID, PROCESSING, SHIPPED, DELIVERED, COMPLETED` (REFUNDED / CANCELLED / AWAITING_PAYMENT never count, not even as the latest order). Per customer of `sub_orders ⋈ orders`: `orderCount` = valid sub-orders, `first/lastOrderAt` = their `created_at`, `spend` = Σ paid_i (subtotal + shipping − discount − platformDiscount) **per currency** (`Money[]`, alphabetical), `province` = `shipping_address->>'city'` of the latest valid sub-order snapshot (never the street address). Page rows, province and spend: province / spend are separate queries for the page's customer ids only, all inside one REPEATABLE READ transaction (list and detail). Every query is a single `$queryRaw` tagged template with all values bound (`Prisma` is type-only in `@repo/db`, so no `Prisma.sql` composition): optional filters are `(${x} IS NULL OR …)`; instants are bound as ISO strings and compared as `${iso}::timestamptz AT TIME ZONE 'UTC'` (columns are UTC `timestamp(3)`), so results do not depend on the session time zone.
- **Segment SQL ⇔ `classifyCustomer`:** the CASE uses cut-offs computed in JS, `last_order_at < now − lapsedAfterDays·86 400 000 ms` → LAPSED, `< now − atRiskAfterDays·…` → AT_RISK, `order_count ≥ vipMinOrders` → VIP, `≥ 2` → RETURNING, else NEW — the same strict millisecond comparison as core. The CASE exists four times (`customers`, `segmentCounts`, `audienceCounts` here + `crmAudienceIds` in `packages/db/src/crm.ts`, behind `audienceIds`); `test/integration/crm.spec.ts` checks every one against `classifyCustomer` at a fixed `now` on the exact 60 / 180-day boundaries (± 1 ms), per segment. **Change one → change all + the core function.** Thresholds come from `PlatformSettings.crm*` (also editable via `PATCH /platform/settings`; the merged `crmAtRiskAfterDays < crmLapsedAfterDays` is re-checked there).
- **Customer cursor:** opaque `base64url(JSON {s: sort, k: lastOrderAt ISO | orderCount, id: customerId})`; keyset `(sortKey, customer_id) < (k, id)` ordered `sortKey DESC, customer_id DESC`. Decoded with a strict Zod schema; `orderCount` ≤ 2 147 483 647 and `lastOrderAt` a real instant in 1970…9999; garbage, tampered, out of range, or a cursor of the other `sort` → 422 `common.error.validation-failed {field: 'cursor'}`.
- **`resolveAudience(tx, vendorId, filter, now)`** (repository, takes a `Prisma.TransactionClient`, its SQL is `@repo/db` `crmAudienceIds` — `packages/db/src/crm.ts`, shared with the CRM worker, which cannot import `server/`): customers of the vendor (C1) matching the filter — segments ANY, tags ANY (`&&`), bought ANY of `boughtProductIds` in a valid order, `lastOrderAt ≥ now − lastOrderWithinDays` — AND marketing consent (`marketing_opt_in_at IS NOT NULL AND (marketing_opt_out_at IS NULL OR marketing_opt_in_at > marketing_opt_out_at)`). Returns `{ userId }[]` from a lean ids-only query (`audienceIds`, no names / tags / province / spend); vendor ACTIVE is the caller's check. The preview uses `audienceCounts` (one `COUNT(*)` + `COUNT(*) FILTER (WHERE consent)` row), the schedule `hasEligibleAudience` (`LIMIT 1`).
- **Privacy (C4):** no CRM query selects `users.email`, a phone or the address beyond `city`; the spec asserts responses contain no `email` / `phone` keys or values.
- **Scale limit (C1):** stats are computed on read — each list / detail / segments / preview call aggregates ALL valid sub-orders of the vendor (index `sub_orders(vendor_id, status)`), and `resolveAudience` returns every eligible id (the worker inserts them in batches; preview / schedule never materialise rows). Fine for thousands of customers per shop; beyond ~50k valid sub-orders per vendor (or when list p95 > ~300 ms) materialise per-customer stats (`vendor_customers` columns or a table refreshed from order events) and keep the same segment rules.

The request log never contains the token: `pinoHttp.serializers.req` = `redactRequestUrl` (`src/common/log-redaction.ts`) replaces `?token=` values with `[redacted]`. - **Rate limit:** `@RateLimit('unsubscribe')` — own per-IP limit `RATE_LIMIT_UNSUBSCRIBE_MAX` (default 60/`RATE_LIMIT_WINDOW`), looser than `strict` because opting out is a legal right and NATs / mail scanners share IPs; fails closed like `strict`.
- **Golden Rule #3 exemption:** `POST …/read`, `read-all`, `crm/unsubscribe` and `crm/unsubscribe/one-click` carry no `@Idempotent()` — they are naturally idempotent (repeat = same state, no new events), and mail clients sending RFC 8058 `List-Unsubscribe-Post` cannot send an `Idempotency-Key`. The preference `PUT` does require one.

- **SSE on Fastify** (`live-sse.service.ts`): `reply.hijack()` + raw writes, not Nest `@Sse()` — Nest's helper `writeHead`s the raw response and drops headers that Fastify hooks queued on the reply (CORS, helmet). We copy `reply.getHeaders()` and add `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`. The 404 and the Redis subscribe happen before the hijack, so their errors still go through `DomainErrorFilter`. Cleanup (idempotent) runs on client close, write error, terminal event, slow client (> 256 KiB unsent), failed status re-check and module destroy: stop the ping timer, leave the local subscription, `ZREM` the viewer, free the connection slot, end the response (so `app.close()` never hangs on open streams). After a terminal event the stream closes; a reconnecting EventSource then gets 404 and stops. The status is checked before and after joining the channel (a session ending in between is caught) and re-read every 4th ping (closes if no longer SCHEDULED/LIVE — covers a lost terminal event; DB errors keep the stream). Per-instance caps (`request.ip`, which honours `trustProxy`): 20 concurrent streams per IP, 10 000 in total → 429 before any lookup. These are a last line of defence: rate limiting at the edge is expected, and viewer counts are approximate (connections, not people; up to 30 s stale).
- **Fan-out** (`live-realtime.service.ts`): one subscriber connection per instance (`redis.duplicate()`, created on the first SSE client, closed on module destroy), per-session `SUBSCRIBE live:{id}:events` with ref-counting → in-process rxjs `Subject` per session. Chosen over `PSUBSCRIBE live:*:events` so an instance only receives traffic (chat, reactions, viewer counts) for sessions it has viewers for. SUBSCRIBE/UNSUBSCRIBE share the connection, so Redis applies them in order. Incoming messages are re-validated with `LiveEventSchema` and must match their channel's session; invalid ones are dropped + logged. Outgoing events always go through `LiveEventsPublisher` (validated, best-effort).
- **Chat** (`live-chat.service.ts`, Redis only — decision D5): per-user cap → LIVE (cached status) → not muted (`SISMEMBER live:{id}:muted`) → claim `live:{id}:chat-dedupe:{clientMessageId}` with `SET NX EX 600` value `pending` (a concurrent duplicate sees the claim → 409 `common.error.conflict`; a finished one holds the message JSON → 200 replay for the same user, 409 for anyone else) → cooldown (`SET live:{id}:cooldown:{userId} NX PX`, `PlatformSettings.liveChatCooldownSeconds`) → `XADD live:{id}:chat MAXLEN ~ 200` (message id = entry id, `sentAt` = its ms; the entry also stores `clientMessageId`, stripped on read) → store the message under the claim → publish. Any failure before the `XADD` lands (cooldown 429, Redis error) releases the claim + cooldown; the publish is best-effort. Vendor delete turns the dedupe key into a `deleted` tombstone before `XDEL`, so a retry of that `clientMessageId` gets 409 instead of replaying or re-posting it. Text is plain text — clients must render it as text. Needs the `PlatformSettings` row (seeded).
- **Viewers** (`live-viewers.service.ts`): each SSE connection is a member of ZSET `live:{id}:viewers` (score = Redis `TIME` ms, refreshed on each ping). Per instance, per session with ≥ 1 local client, every 5 s one Lua call prunes entries older than 30 s, counts, raises `live:{id}:peak` (Lua max) and tries `SET live:{id}:viewers-tick NX PX 4500`; only the winner publishes `viewers.updated`. The ticker stops with the last local client; a crashed instance's viewers age out after 30 s.
- **Reactions** (`live-reactions.service.ts`): per-user cap → `live:{id}:reaction-rate:{userId}` fixed 1 s window (`SET NX PX 1000` + `INCR` in one MULTI) → LIVE (cached status) → aggregate; pending bursts are flushed on module destroy.
- **Abuse guards** (`live-realtime-guards.ts`): `LiveUserRateLimiter` — `live:user-rate:{userId}`, 20 chat + reaction POSTs per user per second across all sessions, checked before any DB read (rotating random session ids can't multiply lookups). `LiveSessionStatusCache` — public session status cached 1 s per instance, found AND not-found, used by chat send/history and reactions (a status change is seen up to 1 s late there; SSE and transitions read the DB).
- **TTL rule:** every realtime write (chat `XADD`, viewer `ZADD`/tick, peak, mute `SADD`) also sets a 24 h TTL (`LIVE_REALTIME_KEY_TTL_MS`), so a write racing the end (after `EXPIRE` ran) can never leave a key without expiry. Trade-off: a key not written for > 24 h while the session is still LIVE expires (not a realistic broadcast).
- **Timing / limits** (`LIVE_REALTIME_OPTIONS`, `live-realtime.options.ts`): ping 15 s, viewer tick 5 s, stale 30 s, reaction flush 1 s, 10 reactions/s per session, 20 actions/s per user, 20 SSE streams per IP and 10 000 in total per instance, status re-check every 4th ping. Protocol constants, not business tunables — overridden only in tests (`createLiveTestApp({ realtime })`).
- **Scaling:** any number of API instances, no sticky sessions — state is in Redis; each instance holds one subscriber connection plus per-session timers for its own SSE clients only. Proxies must not buffer SSE (`X-Accel-Buffering: no` covers nginx) and must allow long-lived responses (idle timeout > the 15 s ping). Browsers cap ~6 HTTP/1.1 connections per origin — serve over HTTP/2 at the edge. Chat and reaction LIVE checks read Postgres through the 1 s status cache; SSE caps are per instance, so the effective per-IP cap is 20 × instances.
- **Known limits / TODO:** `ListLiveChatMessagesQuerySchema` is server-local (`realtime/live-realtime.dto.ts`) until moved to `@repo/core`; reactions over the per-session limit reuse `live.error.chat-rate-limited` (no dedicated code); no `Last-Event-ID` replay — clients refetch state over REST after (re)connecting. Realtime events carry no revision — on `products.updated` clients refetch the session rather than trust event order. A recording may attach while the session is still LIVE (intended: Cloudflare finalises it after the encoder disconnects, often inside the grace window; playback uses it only once ENDED). Public and vendor lists are capped at 100 with no cursor.

Tests live in `server/test/` (excluded from the build). `jest.config.js` has three projects: **unit** (everything except `test/integration/` and `*.pg.spec.ts` — `auth/`, `common/`, `config/`, `http/` in-process Fastify `inject` with mocked Prisma; no Docker) and **integration** (`test/integration/`, needs Docker; CI runners have it). **pg** (`*.pg.spec.ts`, the live-shopping specs under `test/live/` — their own harness, below; needs Docker). `pnpm --filter @server/api test -- --selectProjects unit` skips Docker; selecting only unit files does too.

### Integration harness (`test/support/`)

- **Containers:** `global-setup.ts` starts ONE Postgres 16 + ONE Redis 7 per `jest` run (only if an integration spec is selected), runs `prisma migrate deploy` (packages/db/prisma) into a template DB, and clones `worker_N` per Jest worker; each worker also gets Redis logical DB N. `integration-env.ts` points `DATABASE_URL`/`REDIS_URL` at the worker's pair. Chosen over a container set per file: start-up + migrations cost ~5s once instead of per file (whole integration suite ≈ 8s wall). Never touches the shared local Postgres/Redis.
- **`createTestApp({ env?, imports? })`** → `TestApp { app, db, redis, env, authHeader(user), signAccessToken(user, roles, vendorId?), reset(), close() }`: the real `AppModule` on Fastify with the same plugins as `main.ts` (keep in sync), pino silenced, rate limits raised to 100000 (override via `env`). It starts from an empty DB (`reset()` = TRUNCATE all tables + FLUSHDB; it refuses to run on a non-`worker_N` database). Call `t.reset()` in `beforeEach` when tests must not see each other's rows. Test-only controllers go in a module passed via `imports` (that module imports `AuthModule` to use `JwtAuthGuard`).
- **Auth:** `await t.authHeader(user)` → `{ authorization: 'Bearer …' }` signed by the real `TokenService` from the user's DB roles (vendor roles only while the vendor is ACTIVE). `t.signAccessToken(user, roles, vendorId?)` crafts arbitrary claims (stale vendorId, revoked role).
- **Factories** (`factories.ts`, re-exported from `test/support`): `makeUser(db, { roles?, vendorId?, email?, … })`, `makeVendor(db, { status?, ownerId?, currency?, commissionBpsOverride? })` → `{ vendor, owner, wallet }` (owner gets `VENDOR_OWNER`), `makeCategory`, `makeProduct(db, { vendorId, status?, currency?, price?, variants?: [{ price?, stockOnHand?, stockReserved?, sku? }], categoryIds? })` (vi/en translations, variants, image), `makeShippingMethod(db, { vendorId, price?, … })`, `makeAddress(db, { userId, isDefault? })`, `makeCoupon(db, { scope?, vendorId?, code?, discountType?, discountValue?, maxRedemptions?, perUserLimit?, … })` (default PLATFORM PERCENT 10%, valid yesterday → +1 year), `makePlatformSettings(db, overrides)`. Amounts are integer minor units; ids are monotonic ULIDs (creation order = id order).
